# 验收

## 原则

- **不信任总结**：worker 说“完成/已测试”不等于完成；读文件、看 diff、跑命令。
- **机械判据优先**：能跑测试/CLI/检查的，不靠主观判断；行为类问题用行为/结果契约。
- **目标产物与变更面分开看**：既要验收产物，也要审阅工作区变更是否越界。
- **用户终审**：主观质量、审美、研究判断由用户决定；leader 只做可机械验证与一致性检查。

## 清单

1. **产物存在**：路径、格式、命名符合任务书；不是占位/空文件。
2. **可运行**：相关 CLI/脚本能跑；测试通过；没有 ImportError/路径错误。
3. **判据通过**：任务书里的验收命令逐条执行，记录输出。
4. **变更面**：`git status` / diff 是否只改允许的目录；有没有误删、误改、生成物入库。
5. **一致性**：与蓝图/设计摘要/既有约定不冲突；新依赖/新路径有记录。
6. **可复现**：关键命令、seed、版本、输入路径足够让用户复跑。

## 返工与升级

- 失败项写成“期望 / 实际 / 证据 / 修正要求”，一次说清。
- 同一问题连续失败 3 次 → 停止返工，向用户升级，附复现与已尝试方案。
- 发现任务书本身有问题（缺输入、验收不可执行）→ 先改任务书，再派发。

## 交付给用户

固定结构：目标、完成项、证据（路径/命令/输出）、未决项、风险、下一步。不要贴大段日志；给路径与关键行。
