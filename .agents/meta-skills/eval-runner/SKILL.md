# Eval Runner

## 目标

判断“改进前/后”的 harness 在同一任务、同一项目快照、同一模型路由下是否真的更好；效果与成本一起看。主观层不可自测，但产出必须经本层检验。

## 任务规格

`sub_root/evals/tasks/<id>/`：

- `prompt.md`：直接照搬真实任务文本，不自造简化题。
- `task.yaml`：任务 id、项目快照、模型路由、预算、判据命令、是否人工终审。
- `checks/`：机械判据（脚本/命令）；行为类问题写成行为/结果契约。
- 任务由用户核定入库；过期任务退役或重定基线，留记录。

## 运行

- 优先 `dsh --profile headless "<prompt>"`，隔离工作区 + 私有 `DSH_HOME`；需要细粒度事件/token 时用 SDK。
- 记录：效果（判据通过/人工结论）、成本（token、墙钟、轮次）、失败原因、证据路径。
- 同一任务多轮运行取稳定结论；不要用单次偶然结果下结论。
- 运行产物在 `sub_root/evals/runs/`（不入库）；报告在 `reports/`。

## A/B

- base 臂：当前 harness；delta 臂：base + 改进 patch。
- 同一任务、快照、模型路由；先聚焦任务，默认再跑全部有效黄金任务做不劣化回归。
- 结论：提升 / 无差异 / 劣化；无差异也要如实记录（可能是天花板）。
- 只有切实有效且不劣化的改进才建议实装；由用户终审。

## 预审表

每次对比产出预审表：按人审要点逐项填“初判 + 证据引用”（路径/行/命令输出）。用户复核表格，而不是从头读全部日志。

## 台账

`sub_root/evals/reports/improvement-ledger.md` 记录：问题来源、改动、基准结果、成本、是否实装、回滚点。失败与无效改动同样记录。

## 边界

- 不改判据、不改项目代码、不改蓝图；只改 harness patch 与 eval 任务（任务入库需用户核定）。
- 不隐藏失败；不把“没测出差异”写成“有效”。
