# 哲学（详版）

## 1. 蓝图原则

本条关于项目的最高准则和顶层设计理念。详细内涵可分为三部分：

### 1.1 蓝图优先原则

“蓝图”是用户唯一维护面（内在动因是“用户维护面最小化”愿景），永远最新，不会过时，因此在本项目中具有最高决策效力。其他决策与之冲突时以蓝图为准。若 Agent 认为有必要，可向用户提出蓝图修改请求，但不得在不通知用户的情况下自行修改。

### 1.2 分层蓝图体系的构成

- **设计哲学**：分为简版（`AGENTS.md`）和详版（本册）。用户精心维护，Agent 不主动参与维护。
- **设计摘要**：用户与 Agent 协商确定，仅包含关于项目整体/某一方面的、凝练的自然语言设计目标，不包含具体实现细节。

以上内容位于 `AGENTS*.md` 和 `blueprint-canon` 技能中，应在有必要时积极查阅。

### 1.3 关于“详细设计方案”

在设计摘要敲定后，根据设计摘要细化产生，用于后续实施。由 Agent 编写，用户可选审阅。用完即归档，**不属于蓝图的一部分**，不具有最高决策效力——仅为中间产物，允许漂移和过时，未必最新。计划统一放 `sub_root/others/plans`。

## 3. 自包含与勤分类原则

本条关于项目目录的组织。详细内涵可分为两部分：

### 3.1 自包含原则

**全局层面**：对于一切依赖/配置，能留在项目目录内的，就不外放到外部/用户级/系统级目录。目前机器级只保留两类：系统 PATH、shim 路由层（只转发，不装东西）。git / node / npm / uv / Python / DSH 本体与 Python 包全部在项目内。

**子目录层面**：子目录力求自包含、语义清晰。子目录间应保持松耦合——此为常见 OOP 原则，不需过多赘述。

#### 根目录布局约定

根目录只允许版本控制与 agent 元数据：`.git/`、`.gitignore`、`.gitattributes`、`.agents/`、`AGENTS*.md`。其余一切——Python 工程（`pyproject.toml`、`.python-version`、`uv.lock`、`.venv/`）、源码、脚本、资产、本地 `.env`、工具链、DSH 状态、缓存、计划、测试、评估、研究线——全部收纳在 `sub_root/` 下，并按门类继续分层。`sub_root/` 因此同时是 Python 项目根：uv/pytest/ruff 都在那里执行，根目录不含任何工程文件。

#### 技能（skill）的存放位置

DSH 只从特定根目录发现技能。本项目按角色分三套技能面：worker 用 `.agents/skills`，leader 用 `.agents/leader-skills`，meta 用 `.agents/meta-skills`；三者共享的只读蓝图放 `.agents/shared-skills`。preset 通过 `customSkillDirs` 精确挂载，`includeDefaultRoots: false`，避免跨角色泄漏。

#### 命名约定

目录与文件名统一使用下划线（如 `deps_manager`），不使用连字符；只有生态硬性要求时才例外（npm 包名、DSH 技能名要求 kebab-case）。技能目录名用 kebab-case，Python 包名用 snake_case。

### 3.2 勤分类原则

目录组织偏好：**对并列关系较严格，对父子关系较宽松**。一旦同级文件/目录数量达到三个以上，就应考虑是否存在分类可能；反对平铺式大目录，推荐深层级、语义清晰的分类。

举例来说——对于目前同级并列的 A（子目录）、B（文件）、C（子目录）三元素，若有两者之间相比第三者（例如 A 与 B）存在更强的语义上的相似或关联，就应考虑合并为一个子文件夹，而不是保持三者并列。也即，我们反对平铺式的目录结构（一个大文件夹里有一堆子项），而推荐深层级式的目录结构——几个子目录/文件允许并列，仅当它们之前的关系和地位的确是严格平等的，不存在其中一部分比另一部分关系更近的情况。

本条只是美学偏好，当程序（例如第三方依赖）对文件位置和目录结构有硬性要求时，可忽略本条规则。

## 4. 原地文档原则

本条关于注释和文档策略。

### 4.1 源代码即真源

作为无发布需求的个人项目，本项目不维护独立文档，除蓝图已明确的事项外，一切末端细节的唯一真源即源代码文件。因此，应编写较详细的注释和 docstring（必要时使用总结/概述）以提高可维护性，并积极使用自文档化机制（例如在报错中详细注记正确使用方式）。

特别地，对于技术选型，积极使用**原地** ADR（Architecture Decision Record）：在决策发生的地方用注释记录“选了什么/弃了什么/为什么”，不额外维护 ADR 文档，避免同步地狱。项目的真理只有两个层级——顶层的蓝图（优先）和底层的源代码，不存在独立文档/参考手册等中间层级。且原则上蓝图不写具体路径，定位靠实时检索，以减少漂移风险。

## 5. 极简原则

本条关于本项目对破坏性变更、兼容性与鲁棒性的偏好。

### 5.1 单一实现、不留退路

作为无分发需求的个人项目，开发倾向于**大刀阔斧的破坏性变更**：默认情况下所有功能**仅保留唯一的最新正确路径**实现，**不向后兼容**，**不设置回退**，绝不为同一功能保留两套实现——该默认行为无需请示用户。非最新实现的执行路径应直接**报错**，而非继续运行。

若 Agent 认为需要进行向后兼容设计或回退设计，应向用户明确请示；且原则上一切回退与向后兼容路径必须**显式告警“已弃用”**，严禁静默回退。

个人项目的错误修复和迭代非常快捷（对所有代码有完全修改权力），但长期全面维护非常困难（个人精力有限），因此牺牲鲁棒性来降低代码量是值得的——该策略有助于减少冗余代码，提高可维护性。
