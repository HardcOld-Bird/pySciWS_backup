# 哲学（详版）

## 1. 蓝图原则

本条关于项目的最高准则和顶层设计理念。详细内涵可分为三部分：

### 1.1 蓝图优先原则

“蓝图”是用户唯一维护面（内在动因是“用户维护面最小化”愿景），永远最新，不会过时，因此在本项目中具有最高决策效力。其他决策与之冲突时以蓝图为准。若 Agent 认为有必要，可向用户提出蓝图修改请求，但不得在不通知用户的情况下自行修改。

### 1.2 分层蓝图体系的构成

- **设计哲学**：分为简版（`AGENTS.md`）和详版（本册）。用户精心维护，Agent 不主动参与维护。
- **设计摘要**：用户与 Agent 协商确定，仅包含关于项目整体/某一方面的、凝练的自然语言设计目标，不包含具体实现细节。
- **角色工作说明**：`AGENTS.leader.md`、`AGENTS.meta.md` 是各自 preset 的常驻规程，属于蓝图的人类维护面。

以上内容位于 `AGENTS*.md` 和 `blueprint-canon` 技能中，应在有必要时积极查阅。

### 1.3 关于“详细设计方案”

在设计摘要敲定后，根据设计摘要细化产生，用于后续实施。由 Agent 编写，用户可选审阅。用完即归档，**不属于蓝图的一部分**，不具有最高决策效力——仅为中间产物，允许漂移和过时，未必最新。计划统一放 `sub_root/others/plans`。

## 3. 自包含与勤分类原则

本条关于项目目录的组织。详细内涵可分为两部分：

### 3.1 自包含原则

**全局层面**：对于一切依赖/配置，能留在项目目录内的，就不外放到外部/用户级/系统级目录。目前机器级只保留三类：系统 PATH、`common\bin` 的 shim 路由层（只转发，不装东西），以及无法项目内安装的外部软件（COMSOL、Blender、TeX Live、LibreOffice、NI-DAQmx 驱动等）。git / node / npm / uv / Python / DSH 本体与 Python 包全部在项目内：工具安装物在 `sub_root/deps_management/deps/`，缓存与包在 `sub_root/deps_management/cache/`，版本清单是 `sub_root/deps_management/toolchain.json`。

**子目录层面**：子目录力求自包含、语义清晰。例如，项目 DSH 的配置与状态集中在 `sub_root/deps_management/deps/node/modules/dsh_home/`；分层测试集中在 `sub_root/tests` 与 `sub_root/evals`；技能文档按角色分在 `.agents/skills`、`.agents/leader-skills`、`.agents/meta-skills`，共享蓝图在 `.agents/shared-skills`。子目录间保持松耦合。

#### 根目录布局约定

根目录只允许版本控制、agent 元数据与不可收纳项：`.git/`、`.gitignore`、`.gitattributes`、`.agents/`、`AGENTS*.md`、`pyproject.toml`、`.python-version`、`.env`（本地）。`.venv/` 是 uv 的固定例外，留在根目录但属于项目内。其余一切——工具链、DSH 状态、缓存、计划、测试、评估、研究线——都收纳在 `sub_root/`、`src/`、`scripts/`、`data/` 下，并按门类继续分层。

#### 技能（skill）的存放位置

DSH 只从特定根目录发现技能。本项目按角色分三套技能面：worker 用 `.agents/skills`，leader 用 `.agents/leader-skills`，meta 用 `.agents/meta-skills`；三者共享的只读蓝图放 `.agents/shared-skills`。preset 通过 `customSkillDirs` 精确挂载，`includeDefaultRoots: false`，避免跨角色泄漏。

#### 命名约定

目录与文件名统一使用下划线（如 `deps_manager`），不使用连字符；只有生态硬性要求时才例外（npm 包名、DSH 技能名要求 kebab-case）。技能目录名用 kebab-case，Python 包名用 snake_case。

### 3.2 勤分类原则

目录组织偏好：**对并列关系较严格，对父子关系较宽松**。一旦同级文件/目录数量达到三个以上，就应考虑是否存在分类可能；反对平铺式大目录，推荐深层级、语义清晰的分类。仅当程序（第三方依赖、工具约定）有硬性要求时才忽略。

## 4. 原地文档原则

### 4.1 源代码即真源

作为无发布需求的个人项目，本项目不维护独立文档，除蓝图已明确的事项外，一切末端细节的唯一真源即源代码文件。因此，应编写较详细的注释和 docstring（必要时使用总结/概述）以提高可维护性，并积极使用自文档化机制（例如在报错中详细注记正确使用方式）。

特别地，对于技术选型，积极使用**原地** ADR（Architecture Decision Record）：在决策发生的地方用注释记录“选了什么/弃了什么/为什么”，不额外维护 ADR 文档，避免同步地狱。项目的真理只有两个层级——顶层的蓝图（优先）和底层的源代码，不存在独立文档/参考手册等中间层级。

技能文档（`SKILL.md`）是“面向 Agent 的调用面”，不是独立文档：它只写领域决策、入口与索引，细节进同目录 `references/` 或源码。

---

## 5. 极简原则

### 5.1 单一实现、不留退路

作为无分发需求的个人项目，开发倾向于**大刀阔斧的破坏性变更**：默认情况下所有功能**仅保留唯一的最新正确路径**实现，**不向后兼容**，**不设置回退**，绝不为同一功能保留两套实现。非最新实现的执行路径应直接**报错**，而非继续运行。

若 Agent 认为需要进行向后兼容设计或回退设计，应向用户明确请示；且原则上一切回退与向后兼容路径必须**显式告警“已弃用”**，严禁静默回退。

个人项目的错误修复和迭代非常快捷（对所有代码有完全修改权力），但长期全面维护非常困难（个人精力有限），因此牺牲鲁棒性来降低代码量是值得的——该策略有助于减少冗余代码，提高可维护性。
