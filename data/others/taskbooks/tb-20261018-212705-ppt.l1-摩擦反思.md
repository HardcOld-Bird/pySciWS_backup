# L.l1 harnessing 摩擦反思（tb-5 开题PPT制作）

## 摩擦反思

回顾 tb-5 全程（拆解 → w1/l1/f1/l2/w2 → G2.r1/d1 → w3 抛光），harnessing 指导面总体
充分：plan-decomposition 速查表让拆解一次成型，验收纪律 §4 的信息架构判据直接可用，
任务书延迟书写 + 原始要求自动附送省去了大量复抄。真实摩擦集中在 4 处：

1. **路由卡片表述失真（误导类，最重）**：`plan advance --task` 派发后，[NEXT] 路由卡片
   仍显示「位置：…w1… 动作：书写本环节任务书并派发」——该环节已入队在跑。此后每次
   watch 唤醒的卡片**长期滞后在 G1.P1.w1**，与工作清单（正确显示在途/可派发）互相矛盾。
   另卡片头部「大任务 （无关联任务书）」在 taskbooks link 已完成后仍如此显示。按卡片
   字面行动会重复派发已入队环节。
2. **建议正文无 CLI 查看入口**：`pysci-orch suggestions show <id>` 不存在（仅有 ack），
   审批（approve 要求带判决包理由）前只能自行 `cat orchestration/state/suggestions/<id>.md`
   翻文件。本轮 4 条建议（tier-a/lit×2/writing/reviewer）全部靠翻文件才看到正文。
3. **`bench seen` 只收单 id**：一次传 6 个 id 报 `unrecognized arguments`，且错误信息
   未说明只收一个；清 6 项积压要跑 6 次命令。
4. **state 面手动提交负担**：merge_dirty_face 纪律要求派发前提交 state 脏面，交付留档
   已有自动提交钩子（「新留档即提交」自动生成），但 plan YAML/任务书/建议/回复等其余
   state 变更要组长每轮手动 `git add orchestration/state && git commit`——本轮手动提交
   7 次同型 chore(state) 提交，纯机械重复。

## 改进清单

| # | 摩擦 | 立单方向 | 预期收益 |
|---|---|---|---|
| 1 | 路由卡片滞后/失真（已派发环节仍显示「派发」动作；「（无关联任务书）」与 link 状态不符） | 修卡片生成：动作栏取自工作清单真实状态（在途→「等待完成事件」），taskbook 关联状态正确回显 | 消除按卡重复派发的误导风险 |
| 2 | suggestions 正文无 CLI 入口 | `suggestions show <id>`（或 `suggestions list --full`）输出正文与证据段 | 审批判决包不再靠翻文件 |
| 3 | bench seen 单 id | 接受多 id（nargs='+'）或错误信息注明单收 | 清积压一命令完成 |
| 4 | state 手动提交重复 | 自动提交钩子扩展到 orchestration/state 全域（或 `orch state-commit` 一键） | 消除每轮手动 chore(state) |

## 结论

4 项均为工具面小改（无架构级问题）；无 harnessing 指导缺失、无「表述与实际行为不符」
之外的误导。改进单移交 L.l2 拆解派单、L.l3 派 devops 实施。空清单情形不适用。
