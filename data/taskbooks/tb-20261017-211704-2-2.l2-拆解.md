## 拆解

l3 改进实施拆为 **1 单 devops、2 个工作包**（两面不同工具族，同单交付、验收分面）：

### 工作包 A：orch CLI 引导一致性（F1/F3/F4/F5，落点 `src/pysci/skills/orchestration/tools/`）

| # | 条款 | 验收 |
|---|---|---|
| F1 | **环节规格可回看**：`plan advance --dry`（或等价查询入口）在环节已入队/待证据状态下仍可回打「粗描述+evidence 标题段+收尾命令」；实现以 `ROLE_EVIDENCE_SECTIONS`（plans.py:93）为单一真源打印 | 任一 self 环节在途时执行查询命令能复得规格 |
| F3 | **`status --brief`**：`pysci-orch status --brief` 一页输出——计划进度（x/y＋当前环节）、成员队列在途计数、事件水位、大任务队首 | brief 输出 ≤30 行且含上述四要素 |
| F4 | **引导文案口径统一**：所有规格打印/引导中的收尾命令改为裸 `pysci-orch …`（basic.md §3「首选裸命令」；fallback `uv run --no-sync` 仅注释性提及） | grep 引导打印面无 `uv run --no-sync pysci-orch` 残留 |
| F5 | **`plan reassign --step` 双形态**：短 yaml id（`b2`）与显示名（`B.b2`）皆接受；或最小改法=报错文案注明「--step 用显示名（如 B.b2）」（二选一，取实现成本低者） | `--step b2` 与 `--step B.b2` 同效（或报错含形态说明） |

### 工作包 B：docx 标注机械核验器（F2，落点 `src/pysci/skills/document_writing/tools/`）

- `pysci-compose` 增子命令 **`docx marks <docx> [--para <关键词>]`**：抽取 run 级标注
  （strike / highlight / shd 底色 / bold / color），按段输出「标注类型+颜色+文本片段」，
  退出码 0；`--para` 过滤目标段（关键词命中段文本）。
- 设计输入＝本轮实测惯用的 zipfile+regex 抽取面（`w:strike`、`w:shd w:fill="FF0000|FFFF00"`、
  `w:b`）；输出供人读与 grep（reviewer G10、writing 自检 6 的机械对照面）。
- 测试：用 v3 docx 类样张（红删 FF0000＋黄粗 FFFF00）断言抽取正确；补 docx 缺标注/纯文本
  两负例。

### 实施要求

- 两包各带测试（pytest 挂既有 tests 面）；全量测试通过后合并；
- 遵 devops 交付协议；**不动**用户刚改的推送面（taskbooks 要求与历史总览组装逻辑）；
- 工作包 B 若与 `compose` 既有子命令风格冲突，以既有风格为准（如 `slides geometry`
  的输出口径）。

### 成员与白名单

- 成员：devops；`--dirs src/pysci/skills/orchestration src/pysci/skills/document_writing tests`；
- 验收预期：F1/F3/F4/F5 逐条可测（各 1 条 pytest 或命令级演示）；`compose docx marks`
  对修改稿v3.docx 输出含 `FF0000`/`FFFF00`/strike/bold 样本且 `--para Infinite EP` 命中段 92。
