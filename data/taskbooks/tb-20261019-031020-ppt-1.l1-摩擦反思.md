# L.l1 harnessing 摩擦反思（tb-5 返工第 1 轮）

## 摩擦反思

返工轮流程（rework 骨架→a1–a5→b1–b_last）整体顺畅：jury gate、任务书历史自动附送、
state-commit/suggestions show/bench seen 多 id 等初版改进全部兑现好用。本轮真实摩擦 2 处
＋1 处知悉项：

1. **`plan advance` 输出被「要求与历史总览」淹没（最耗轮次）**：每次 advance 先打印
   ~35KB 的任务书历史全文，真正的输出（入队确认/工作清单/交接决策）沉底——派发确认
   看不到，只能再跑 `plan advance`/grep 尾部二次确认（本轮为此多花 4+ 次查询；两次
   grep 还被表格行噪声污染）。历史总览对**首次**引导有附送价值，对同一 plan 的后续
   advance 是纯遮挡。
2. **`plan adhoc` 计划 id 撞车**：同分钟两个 adhoc（writing p10 裁切、devops c 口径）
   都登记为 `adhoc-20261019-050159`，两个无关单被合并进同一计划记账（统计 2 跳）。
   本次侥幸无损（两单各自交付正常），但撞车状态下 state 覆盖/对账有丢失风险。
3. **知悉项（无需改进）**：devops 孤儿 worker 事件自动回收复位并重新唤醒，自愈机制按
   设计工作。

## 改进清单

| # | 摩擦 | 立单方向 | 预期收益 |
|---|---|---|---|
| 1 | plan advance 输出被历史总览淹没 | 历史总览仅该 leaf 首次引导附送（或后置/`--full` 才打）；[NEXT]/工作清单前置 | 派发确认一眼可见，省二次查询 |
| 2 | plan adhoc id 同分钟撞车合并记账 | id 加成员/序号后缀或撞车自动递增，保证一单一 plan | 状态记账无覆盖风险 |

## 结论

2 项均为 orch CLI 小改（无架构级问题）；初版 4 项改进经本轮实测全部有效。改进单移交
L.l2 拆解、L.l3 派 devops 实施。空清单情形不适用。
