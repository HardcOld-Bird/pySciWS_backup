〔历轮摘要〕- 初版 tb-20261018-212705-ppt「开题PPT制作」状态=rejected；第 1 轮批语：整体良好，但有如下改进建议：
# 关于文献
对于“Science 334, 333 (2011)”的处理，我实际检查了官方网站的下载流程，发现并未被任何挑战页阻拦，在校园网环境下，认证和登录是全自动的。请问，为何我们的文献获取链路未能成功获取该pdf？我认为唯一可接受的原因是网络不稳定——因为经实测，science对于下载请求的响应似乎不稳定。但如果是我们技术上未打通官网下载这条链路，我建议你积极调查和思考能否通过基础设施改进来实现这一下载渠道——毕竟获取science文章正文对于我们的系统来说很重要。在成功获取正文前，先使用占位符即可。如果这的确不可能，请在返工交付中向我详细解释原因。
# 关于PPT
对于PPT制作（及预设处理方式），整体良好，但我有一些进一步的细节建议，希望能够纳入预设和本次返工，并可于未来零成本复用（包含在“学院正式汇报预设”中）：
1.首先，“个人改进PPT模板.pptx”对于PPT每页标题的处理方式没有被充分模仿——模板中，该标题使用分散对齐，并通过调整文本框长度来赋予标题微小的字间距。当然，我们的目的是字间距，因此如果我的设置方式对于LLM来说不太便利，可以通过其他方式实现，但仍然推荐保留这种字间距。
但对于焦点块标题而言，我强烈建议使用分散对齐，因为该文本框是有背景色的，左对齐将对文本框长度提出精确的设置要求，否则将留下丑陋的可见空白。同样，通过调整长度赋予文本框微弱的边距（实际上，该长度完全是可程序化计算的，根据字符数可大致估计——但我建议它不是完全线性，而是字符数越少，给予的字符边距越大——两个字时间距本身接近一个字宽，字符数越多，额外赋予的每个字符间间距越小）。
2.然后，对于页面底部的“缩略引用文本框”，我发现目前其内容过短，导致文本框右侧有太长的空白。对此，我提议改变方案，不再置于统一文本框内，而是置于多个文本框，每个焦点块使用一个“缩略引用文本框”，并将该文本框的左缘与焦点块的左缘对齐。对于每个文本框，当文献数小于等于3个，应尽量保证一行一个文献，而不是多个文献；四个及以上不受此限制。每页的多个文本框应在上缘对齐，而上缘的对其位置取决于所有文本框中最高（行数最多）的一个——应保证它的下缘直达页面下缘的灰色边框。
3.目前的PPT制作已经有初步的排版意识，这很好，但我有进一步指导建议：
应以这样的逻辑考虑版面——将整个页面矩形，去除顶部页标题占据的一行（高度固定），去除底部“缩略引用文本框”所占的一行（高度取决于其中最高的文本框），剩余的矩形视作“可排版区域”。然后，使用从左到右的横线或者从上到下的竖线来分隔可排版区域矩形（或者已经被切分的子块），以进行分块。有时，单个子块分配给一个焦点块；有时，多个子块属于同一焦点块，但要求它们（曾经）来自同一父级子块（被切分前）——这样这些子块的组合边界框将总是该父级子块（一个紧凑矩形），较为美观。当多个子块属于同一焦点块时，一般来说仅左上方的一个包含焦点块标题即可。对于每个子块，有三种类型，文本块、单图块和多图块，示例分别为“个人改进PPT模板.pptx”第三页左侧/下侧块、第三页右上块，以及第五页右侧块。对于两个单图块相邻，并且（被切分前曾经）来自同一父级子块的情况，建议合并为多图块，而不是保持分离。文本块的边框较细（见“个人改进PPT模板.pptx”第三页），而图像块的边距较粗（这一点现版本已正确设置了）。文本块和多图块可将焦点块标题置于内…

  均为**上=fig5(4250×2509)、下=fig3裁切(3103×2086)**，即指令目标与执行后状态一致，但
  与您要的**互换方向相反**。若「现上=fig3」为假（真为上=fig5），则指令把图又"换"回了
  原样——净效果零变化，与您的「完全没执行」观感完全吻合。
- 性质：成员没有做错——**错在指令**；而指令的错误前提（la3 口头判断）在全链无人对产物
  核验。任务书写「现 X=…」的裸断言是事故源。

**根因 2：索引里的「建议」越权覆盖「占位同款硬优先」（p6/p8 选错图案）**
- 实证链（会话转录 155339d1…jsonl 已查）：la2 索引含挑选建议如「NatCommun7 …补充图用
  fig2」「[6] 补充图首选 fig1…次选 fig2」；w8 会话逐条读到这些「补充图候选」并照办——
  于是草稿占位只有 2 图的中列放了 4 图；w6 同理按「改选 fig1（Fig.6）」放弃了占位同款
  fig5（其时被 la2 判"不完整"）；p8 右列、p10 左列等同模式。**「占位符同款=硬优先」是
  用户原则，却被索引的"建议"级语句压过，成员照建议不照占位符。**
- 性质：事实与建议混装在同一索引文档里，建议没有降级标记；成员没有"建议可违背原则"
  的边界意识，任务书也未再声明占位优先级。

**根因 3：隐性不变量无守护——重建即毁（背景三层、字体方案）**
- 背景实证：模板/草稿的背景三层（灰粗边框、白卡、半透明院徽）是**页形状**（模板 p3
  形状清单含「矩形:圆角×3、图片(院徽)」）；round-1 成品保留（w3_build p3 仍有
  Rectangle1/2+Picture3 装饰）；round-2 的「路径1重造」逐页重建时未列「保留装饰层」
  要求，重建把装饰形状一并清掉（当前成品 p3 仅内容形状、无院徽图；round-2 的 rv 也
  见到「页面内无白卡形状」）。**"背景要保留"从未出现在任何要求清单里——它是隐性不变量，
  重建一碰就碎。**
- 字体实证：成品标题 runPr 只有 `<a:latin typeface="汉仪大宋简">`，**缺 `<a:ea>`**；
  模板同位置为 latin+ea 双设+panose/charset 全参。中文走 ea 槽 → 渲染回落主题默认
  （雅黑/黑体），而 UI 显示仍是汉仪大宋简——与您的观察分毫不差。此为 python-pptx 只写
  latin 的经典坑，round-1 未暴露是因为其标题多为模板占位符原生文本框。

**根因 4：提取管线能力上限与映射混乱未声明（想要的图缺位案）**
- 实证链：提取管线设计为「每篇最多 6 个**最大图区**，fig1…fig6」（lit 初版任务书原文）；
  于是 RPP 86 的 Fig.7、PRL 123 的 Fig.2 根本不在产出集（图区排序按面积，figN≠原文
  图号）；NatMater 18 因用户提供的是**手动批注过的 PDF**，提取全是整页而非 figure（您
  已诊断）。成员挑图时拿着"figN"猜内容，映射全靠 la 标注补。
- 性质：工具能力边界未进任何规格文档；figN 编号体系与原文图号脱钩是持续性混淆源。

**根因 5：成员/组长的自述与产物之间无机械绑定（"报告说做了"≠"产物是这样"）**
- 实证链：w10 报告给出「互换前后对照」且自检 PASS——对照的是**错误指令**；此前 w3
  报告的引用框 PASS 系锚错块（round-2 rv 揪出）；p6 标题串位也是报告没抓到、组长 XML
  实测才抓到。**交付报告的断言没有被任何机械步骤验证**，正确性依赖成员自觉与审查者抽检。

### 与「要求被遗忘」的关系

五条合流即产生您观察到的表象：要求写在批语里→进任务书/索引时被转写（丢真/加戏）→
成员按转写版执行（还可能被建议带偏）→ 重建顺带毁掉没写进要求的既有好状态→报告自称
合格而无机械对账。**每一环都在漏，且没有任何一环强制对账。**

## 结论

主根因是**要求流转链无机械保真**：前提不核验、事实建议不分家、不变量不登记、工具边界
不声明、断言不对账。修复方向（A.a2 详）：以「deck 规格书（spec）+ slides audit 机械审计
+ 任务书 spec 切片生成 + 索引去建议化 + 提取管线补缺」五件套一劳永逸；返工本身按 spec
驱动执行即顺带完成。实现量属中型工具建设（非推倒重构），详见解决方案与向用户汇报要点。

## 解决方案

# A.a2 解决方案报告（tb-5 返工第 3 轮——一劳永逸修复设计）

## 解决方案

总目标：把「要求流转链」的五个漏点逐个焊死，使**要求写了就生效、状态变了就被抓、
报告说了就可验**。五件套（1–2 为骨干，3–5 为配套）：

### 1. Deck 规格书（spec）——要求的唯一真源

每 deck 一份机器可读 YAML（`data/大任务/5_开题PPT/deck-spec.yaml`），两类条目：
- **不变量**（重建不得破坏）：装饰层三层指纹（灰粗边框/白卡/半透明院徽——形状特征+尺寸+
  位置，从模板实测提取）、字体方案（标题/胶囊/正文的 latin+ea+panose 全参，照模板 rPr）、
  版式归属、动画规格指针；
- **变量槽位**（本轮要放对的东西）：每页每图槽＝{占位符指纹（草稿内嵌图 md5/尺寸）、
  内容锚（一句话+原文图号，如「RPP 86 Fig.7 场分布」）、来源文件、裁切参数}；引用框/
  胶囊/标题按预设公式引用（不重复抄参数）。
生成方式：组长+lit 从模板/草稿/图像索引**机械实测**汇编（现状断言全部带读数）。

### 2. `slides audit` 机械审计——断言对账器

`pysci-compose slides audit <deck> --spec <spec>`：逐项机械核验并输出 PASS/FAIL 表：
装饰层存在性与指纹、字体 runPr 含 `<a:ea>`、图槽数量/顺序/内容指纹（md5/尺寸/感知哈希）、
引用框规则、标题公式——能机械判的全机械判（内容同款判定用「占位符指纹比对+尺寸比对」，
判不了的降级为「人工确认」行但必须留勾选痕迹）。
**流程绑定**：每个生产叶交付必须附 audit 本页输出；rv 终检以 audit 全量输出为底稿；
「报告说了」必须有 audit 行支撑（根因 5 的对账器）。

### 3. 任务书 spec 切片生成 + 前言实证制（根因 1/2）

- 派单时按页/工序**从 spec 切片**生成任务书正文（槽位清单即工作清单），杜绝转写丢真；
- 任务书中凡涉「现在是什么状态」的断言**必须附机械读数**（md5/尺寸/形状清单截图式引用），
  禁止裸断言；组长书写时先跑读数（本轮 p10 案的教训固化为流程）；
- **索引去建议化**：图像索引只记事实（内容/尺寸/指纹/原文图号），「建议选 X/补充图 Y」
  类语句全部剥离；挑选决策规则唯一：占位符同款 > 原文图号匹配 > 其余（写入 spec 槽位），
  任何偏移必须在交付报告显式声明理由并经复核（建议不得再越权）。

### 4. 提取管线补缺（根因 4）

- fig 区检测上限可配（默认放开 6 上限）+ **按原文图号靶向提取**（figures.json 增
  figN↔原文图号映射；支持用户批注 bbox 直接落参）；
- 处理整页扫描型 PDF（NatMater 案）：检出"整页即图"模式并提示裁切参数；
- 对本轮已知缺图（RPP 86 Fig.7、PRL 123 Fig.2）重提并入索引。

### 5. 字体与装饰层工具化（根因 3）

- 写框工具/预设强制**字体全槽**（latin+ea+cs+panose 照模板 rPr 复制，python-pptx 的
  latin-only 坑用 XML 补写绕开），audit 机械校验每页标题/胶囊/正文 runPr；
- 重建脚本保留/复原装饰层（从模板页形状层复制三层），spec 登记 + audit 校验存在性。

### 实施与返工组织

- **a5（devops，本轮主战场）**：spec 载体与 schema、`slides audit`、任务书切片辅助、
  提取管线补缺、字体全槽工具——即上文 1–5 的机械面；
- **B 段（返工，次要但作为机制试金石）**：b_spec（组长+lit 汇编 deck-spec，实测生成）→
  w3–w10 每页一单**按 spec 槽位**修复（9+2 项批语 + 字体 + 背景 + 图序），每叶交付附
  audit 输出 → rv 终检（audit 全量 + 抽检）→ d_preset（本轮新规则入预设）→ b_last。

### 向用户汇报要点（按批语要求）

本方案属**中型工具建设**（spec schema + audit 工具 + 流程绑定），非推倒式大重构——
现有 deck/预设/队列体系全部沿用，新增的是「要求真源+对账器」一层。若实施中发现 audit
覆盖面需扩展到动画/几何全量（更大盘子），会在报告中再报。科学内容与版面美学判断仍由
人（用户）终审，机械面只保证「要求不丢、状态不骗」。

## 结论

五根因→五件套一一对应：spec（真源）+ audit（对账）+ 切片生成/索引去建议化（流转保真）+
提取补缺（能力边界）+ 字体/装饰工具化（不变量守护）。返工按 spec 驱动顺带完成，且作为
新机制的首次实战验证。待 A.a3 送审后实施。
