## 摩擦反思

按正式要求三问逐项回顾：

**① harnessing 指导是否充分？** 环节职责与判据总体清晰（evidence 标题段、拆解模板、
验收纪律均有章可循）。不足：**环节 evidence 标题段规格只在推进瞬间打印一次、不可回看**
——B.b1 环节我用 `plan advance` 输出被管道过滤错过规格行，事后只能 `grep` 源码
`ROLE_EVIDENCE_SECTIONS`（plans.py:93）确认「拆解、结论」；`plan advance --dry` 在已
入队状态下亦不回打规格。属真实摩擦（F1）。

**② 信息获取是否方便？** 触发点自动附送「要求与历史总览」改进后 ① 段已含原始要求全文
（格式句在位——推送改进实测通过）；但 ③ 历轮摘要的任务概述/交付摘要仍于「…」处截断
（**观察项**：用户刚改过推送面，待其实测结论，不立单重复改）。真实摩擦两桩：
- **docx 标注机械核验无工具**（F2）：验证「格式标注完备性」（新 G10）需自写 zipfile
  抽 run 级 strike/shd/bold + `compose convert`+`verify` 渲染逐页 Read——reviewer 的
  agents.md 也记载同类「自建 PIL/zipfile 兜底」经历。G10 若无机械核验器，永远只能人肉。
- **`pysci-orch status` 输出 29.8 KB 无简报档**（F3）：每次都要 sed/tail 二次过滤才
  得到计划/队列/事件水位几行核心信息。

**③ 是否存在误导？** 两处：
- **收尾命令引导用 `uv run --no-sync pysci-orch …`**（F4），与 basic.md §3「首选裸
  `pysci-orch`」全员口径相反；全程裸命令实测可用。引导文案应统一为裸命令优先。
- **`plan reassign --step` 只认显示名**（F5）：YAML 里环节 id 是 `b2`，传 `--step b2`
  报「无环节 b2；可用环节：B.b2…」——报错可用清单用显示名、YAML 用短 id，两种形态
  不一致；应两者皆收或报错文案点明「用显示名 B.b2」。

## 改进清单

| # | 摩擦 | 立单改进（l2 拆解、l3 devops 实施） | 类型 |
|---|---|---|---|
| F1 | evidence 标题段规格一次性打印不可回看 | 当前环节规格可重复查询：`plan advance --dry`（或 `taskbooks report`/`next`）在任意时刻回打「粗描述+evidence 标题段+收尾命令」 | usability |
| F2 | docx 标注无机械核验器（G10 人肉） | `pysci-compose` 增 docx 标注检查（如 `compose docx marks <docx> [--para 关键词]`：列出 strike/highlight/shd/bold run 与颜色），供 writing 自检与 reviewer G10 机械对照 | usability |
| F3 | `orch status` 无简报档 | `pysci-orch status --brief`：计划进度/成员队列在途/事件水位/大任务队首一页输出 | usability |
| F4 | 规格打印的收尾命令带 `uv run --no-sync` 前缀 | 引导文案统一「裸 `pysci-orch` 优先」口径（basic.md §3） | usability |
| F5 | `plan reassign --step` 短 id/显示名不一致 | 两种形态皆接受；或报错文案注明「--step 用显示名（如 B.b2）」 | usability |

不立单（观察/设计使然）：历轮摘要截断（用户推送改进待实测）；evidence 收尾与在途结算
分两步（交接决策点有意设计）；任务书需手抄真源事实（内容判断本职）。

## 结论

- 五桩真实摩擦全部 usability 类、无 defect；立单 5 条（F1–F5），核心两条是
  **F2（docx 标注机械核验——直接配套本轮新 G10 判据）**与 **F1（规格可回看）**；
- F4/F5 属引导文案与参数形态的低成本一致性修复，同批捎带；
- 与用户推送改进的边界：历轮摘要截断如实记录为观察项，不重复立单；
- 流程：本报告 → l2 拆解改进派单 → l3 派 devops 实施；随后全流程报告交付用户裁决。
