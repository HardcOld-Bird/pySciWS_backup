1. **路由卡片表述失真（误导类，最重）**：`plan advance --task` 派发后，[NEXT] 路由卡片
   仍显示「位置：…w1… 动作：书写本环节任务书并派发」——该环节已入队在跑。此后每次
   watch 唤醒的卡片**长期滞后在 G1.P1.w1**，与工作清单（正确显示在途/可派发）互相矛盾。
   另卡片头部「大任务 （无关联任务书）」在 taskbooks link 已完成后仍如此显示。按卡片
   字面行动会重复派发已入队环节。
2. **建议正文无 CLI 查看入口**：`pysci-orch suggestions show <id>` 不存在（仅有 ack），
   审批（approve 要求带判决包理由）前只能自行 `cat orchestration/state/suggestions/<id>.md`
   翻文件。本轮 4 条建议（tier-a/lit×2/writing/reviewer）全部靠翻文件才看到正文。
3. **`bench seen` 只收单 id**：一次传 6 个 id 报 `unrecognized arguments`，且错误信息
   未说明只收一个；清 6 项积压要跑 6 次命令。
4. **state 面手动提交负担**：merge_dirty_face 纪律要求派发前提交 state 脏面，交付留档
   已有自动提交钩子（「新留档即提交」自动生成），但 plan YAML/任务书/建议/回复等其余
   state 变更要组长每轮手动 `git add orchestration/state && git commit`——本轮手动提交
   7 次同型 chore(state) 提交，纯机械重复。

## 改进清单

| # | 摩擦 | 立单方向 | 预期收益 |
|---|---|---|---|
| 1 | 路由卡片滞后/失真（已派发环节仍显示「派发」动作；「（无关联任务书）」与 link 状态不符） | 修卡片生成：动作栏取自工作清单真实状态（在途→「等待完成事件」），taskbook 关联状态正确回显 | 消除按卡重复派发的误导风险 |
| 2 | suggestions 正文无 CLI 入口 | `suggestions show <id>`（或 `suggestions list --full`）输出正文与证据段 | 审批判决包不再靠翻文件 |
| 3 | bench seen 单 id | 接受多 id（nargs='+'）或错误信息注明单收 | 清积压一命令完成 |
| 4 | state 手动提交重复 | 自动提交钩子扩展到 orchestration/state 全域（或 `orch state-commit` 一键） | 消除每轮手动 chore(state) |

## 结论

4 项均为工具面小改（无架构级问题）；无 harnessing 指导缺失、无「表述与实际行为不符」
之外的误导。改进单移交 L.l2 拆解派单、L.l3 派 devops 实施。空清单情形不适用。

# L.l2 改进拆解派单（tb-5 开题PPT制作）

## 拆解

依据 L.l1 摩擦反思（`data/taskbooks/tb-20261018-212705-ppt.l1-摩擦反思.md`）的 4 项改进
清单，拆解为 devops 可一次性实施的工单。四项同属 orch CLI/钩子工具面，彼此正交、可同批
实施；按「一项一验收」给出验收判据。

**工单 1：路由卡片状态失真修复（最高优先）**
- 现象：`plan advance --task` 入队后，[NEXT]/watch 路由卡片的「动作」栏仍显示「书写本
  环节任务书并派发」指向已入队环节，且长期滞后在首个环节（实测全程卡片停在
  G1.P1.w1）；头部「（无关联任务书）」与 `taskbooks link` 已完成状态不符。
- 修法：卡片生成逻辑改取工作清单真实状态——在途环节显示「等待完成事件」，「派发」动作
  只出现在真可派发环节；taskbook 关联状态从 taskbooks/plan 关联记录回显。
- 验收：派发任一环节后抓取下一次卡片输出，动作栏≠「派发」该在途环节；link 后头部不再
  显示「无关联任务书」。

**工单 2：`suggestions show <id>` 入口**
- 现象：审批需带判决包理由，但 CLI 无法看建议正文，只能 cat state 文件。
- 修法：`pysci-orch suggestions show <id>`（输出 kind/正文/证据/success_criteria；
  已审批的从 approved/rejected 目录同样可查）；或 `suggestions list --full`。
- 验收：`suggestions show` 对未审批与已审批 id 均输出完整正文；无 id 时报用法。

**工单 3：`bench seen` 多 id**
- 现象：传多 id 报 unrecognized arguments，且未说明单收。
- 修法：`bench seen <id>...`（nargs='+'）逐项标记；或维持单收但错误信息注明「一次一个」。
- 验收：一条命令标记多项成功；错误路径有明确用法提示。

**工单 4：state 面自动提交扩展**
- 现象：交付留档有「新留档即提交」自动钩子，但 plan/建议/回复等 state 变更需组长每轮
  手动 chore(state) 提交以防 merge_dirty_face 拦组员合并（本轮手动 7 次）。
- 修法（择一，实施者定）：①自动提交钩子覆盖面扩到 orchestration/state 全域（沿用
  「新留档即提交」口径）；②提供 `pysci-orch state-commit` 一键提交该目录。
- 验收：模拟 plan/建议文件变更后，无需手动 git 操作即不脏（或一键命令一步清账）；既有
  自动提交行为不回归。

**派单口径**：四项均交 devops 一并实施（同批一份任务书即可，各带回归测试）；工单 1 优先。
无成员侧行为变更，不涉规则文件裁决。空改进清单情形不适用（本轮有 4 项）。
