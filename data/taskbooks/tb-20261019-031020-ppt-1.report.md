# 关于PPT
对于PPT制作（及预设处理方式），整体良好，但我有一些进一步的细节建议，希望能够纳入预设和本次返工，并可于未来零成本复用（包含在“学院正式汇报预设”中）：
1.首先，“个人改进PPT模板.pptx”对于PPT每页标题的处理方式没有被充分模仿——模板中，该标题使用分散对齐，并通过调整文本框长度来赋予标题微小的字间距。当然，我们的目的是字间距，因此如果我的设置方式对于LLM来说不太便利，可以通过其他方式实现，但仍然推荐保留这种字间距。
但对于焦点块标题而言，我强烈建议使用分散对齐，因为该文本框是有背景色的，左对齐将对文本框长度提出精确的设置要求，否则将留下丑陋的可见空白。同样，通过调整长度赋予文本框微弱的边距（实际上，该长度完全是可程序化计算的，根据字符数可大致估计——但我建议它不是完全线性，而是字符数越少，给予的字符边距越大——两个字时间距本身接近一个字宽，字符数越多，额外赋予的每个字符间间距越小）。
2.然后，对于页面底部的“缩略引用文本框”，我发现目前其内容过短，导致文本框右侧有太长的空白。对此，我提议改变方案，不再置于统一文本框内，而是置于多个文本框，每个焦点块使用一个“缩略引用文本框”，并将该文本框的左缘与焦点块的左缘对齐。对于每个文本框，当文献数小于等于3个，应尽量保证一行一个文献，而不是多个文献；四个及以上不受此限制。每页的多个文本框应在上缘对齐，而上缘的对其位置取决于所有文本框中最高（行数最多）的一个——应保证它的下缘直达页面下缘的灰色边框。
3.目前的PPT制作已经有初步的排版意识，这很好，但我有进一步指导建议：
应以这样的逻辑考虑版面——将整个页面矩形，去除顶部页标题占据的一行（高度固定），去除底部“缩略引用文本框”所占的一行（高度取决于其中最高的文本框），剩余的矩形视作“可排版区域”。然后，使用从左到右的横线或者从上到下的竖线来分隔可排版区域矩形（或者已经被切分的子块），以进行分块。有时，单个子块分配给一个焦点块；有时，多个子块属于同一焦点块，但要求它们（曾经）来自同一父级子块（被切分前）——这样这些子块的组合边界框将总是该父级子块（一个紧凑矩形），较为美观。当多个子块属于同一焦点块时，一般来说仅左上方的一个包含焦点块标题即可。对于每个子块，有三种类型，文本块、单图块和多图块，示例分别为“个人改进PPT模板.pptx”第三页左侧/下侧块、第三页右上块，以及第五页右侧块。对于两个单图块相邻，并且（被切分前曾经）来自同一父级子块的情况，建议合并为多图块，而不是保持分离。文本块的边框较细（见“个人改进PPT模板.pptx”第三页），而图像块的边距较粗（这一点现版本已正确设置了）。文本块和多图块可将焦点块标题置于内部左上角（见“个人改进PPT模板.pptx”第7页），单图块最简单，仅为图。为保持排版美观，我们要求每个焦点块的轮廓都呈现一个饱满的矩形，并且当页所有内容组合起来填满所有可用空间，各级子块间距固定（并且按层级区分联系紧密度，焦点块之间间距稍宽，同焦点块的不同子块之间间距较窄），没有时宽时窄。这一点是我们的现有版本明显未做到的一点，建议集中改进。为保证这种“饱满性”，有许多技巧：
挑选对应文章中合适的图像（第一张图优先级最高，其次是实验图，拿不准就参考占位符来），然后调整其缩放比例，使相邻的多幅图等宽或等高。如果这种缩放导致图的内容看不清而不可行，则可以不保证这一点，转而使用多图块——它不要求内部图像严格等宽或等高（但不要差太多，建议比例不要比1.5:1更悬殊），因为它用一个统一的白色背景将所有图像包含在内。如果两幅相邻图像的长宽比差距过大，导致近似等宽/等高都不可行，那么则应通过巧妙添加一个文本块，并在其中书写内容的方式，使“相邻图像+文本块”这个整体呈现饱满的矩形。
以及，对于同一页的多个焦点块标题，如果可以水平（上缘）对其或竖直（左缘）对齐，则应尝试保持对齐。
以上流程已经比较好地具有机械判定的可行性，建议开发基础设施实现这一点的机械处理，或添加为规程使组员手动处理（具体哪种方案由你决定）。
4.第三页建议沿用“手工草稿.pptx”的左中右三板块布局。

# A.a1 成因分析（tb-5 返工第 1 轮）

## 成因分析

### 一、Science 334, 333 (2011) 获取失败（用户重点质询）

**实测取证（2026-10-19，本机，直连未走代理）**：
- `curl -L https://www.science.org/doi/pdf/10.1126/science.1210713` 连打 3 次：**全部
  HTTP 403**，响应体 5,509B HTML，`<title>Just a moment...</title>`、引用
  `challenges.cloudflare.com`——**Cloudflare JS 挑战页（bot 防护）**。
- 换浏览器 UA、试 `epdf` 形态再打 2 次：仍 403（5,723B 同挑战页）。
- 结论：**不是「网络不稳定」**——本机 curl 5 连击稳定被挑战；所谓不稳定感来自
  Cloudflare 自适应评分对不同客户端/时段松紧不一（用户浏览器得分高即放行）。

**为何用户浏览器能过、我们不能**：Cloudflare JS 挑战须由**真浏览器执行 JS**换
`cf_clearance` cookie；校园网下机构认证（SSO）是透明的，用户浏览器拿 cookie 后直接
到 PDF。纯 HTTP 客户端（requests/curl，无论 UA）在 TLS 指纹与 JS 挑战双检下必 403——
这与 backlog #232 已实证的「curl 200 vs requests 403」（APS 仅 TLS 指纹检）不同，
Science 是**更严的 JS 挑战**，curl 也过不去。

**我们链路的断点**：`browser_fetch.py` 的设计目标正是「Playwright 复用本机 Chrome/Edge
过 CF」（模块头注释明示），且 playwright 依赖已装（实测 import OK）。但 l2 当日六渠道
尝试记录中**没有浏览器通道的尝试痕迹**（渠道表：本地/Zotero/Science 直链 403/read
Cloudflare/arXiv 无/S2 CLOSED）——断点在**调用链**而非能力缺失，候选疑点（留 a5 实证
定位）：①`read` 的渠道候选序里浏览器通道排在末位且前序失败后未被触发或静默失败；
②headless 默认启动被 CF 指纹识别（工具已备 `--headed` 形态）；③挑战页出现后未等待
JS 完成即判失败。此外 Science 无专属 PublisherAdapter（仅 APS+generic），但 generic
兜底不阻下载，属次要。

**可修性评估：高**。所需组件（Playwright、本机浏览器、PDF 下载命令、CF 挑战特征词表
`"checking your browser"` 等）已存在，缺的是「挑战等待→clearance→PDF 落盘」链路打通
＋science.org 适配＋按用户提示的重试语义（其观察的不稳定恰可由 N 次重试吸收）。

### 二、PPT 版面与预设差距（用户 3 项机制性建议 + 8 项逐页改法）

- **标题字间距/分散对齐**：w1 预设只记了「框宽随字数自适应、algn=dist」的实测值，未把
  「字间距是目的、框长是手段」提炼为可复用规则；焦点块胶囊标题的分散对齐需求未被识别
  （背景色框+左对齐=右侧可见空白）。
- **缩略引用文本框**：预设照抄模板「页底一框」形态，未识别用户真实意图（按焦点块分框、
  左缘对齐、行数规则、上缘统一、下缘触灰边）——模板是手段，意图才是规格。
- **饱满排版**：w2/抛光均为手工摆放，无「递归切分+三类子块+间距层级」的排版代数；「满」
  只有目标没有可执行构造法，导致间距时宽时窄、块轮廓不饱满（用户点名的现有版本主要缺陷）。
- **逐页布局**：初版未按草稿的左中右/左右构图落位（如 p4/p5 左侧应为手绘内容块而非文章
  图）；p9 漏放 PRApplied 25 054054 的图（3 篇只落 2 图，占位图对应关系被丢）。
- **机制性保证缺口**：geometry 机械闸只管描边/互叠/越界，**无排版饱满度/对齐/间距判据**，
  审美规格全靠成员自觉——用户已明示「机械处理或规程化，由我决定」。

## 结论

1. Science 334 失败根因＝**Cloudflare JS 挑战**（非网络不稳、非机构权限），我们的
   Playwright 过 CF 能力在调用链上未生效；基础设施改进可打通（a2 给方案）。
2. PPT 差距根因＝预设提炼停留在「模板实测值」层，未升维到「用户意图规则」；且缺排版
   构造法与机械判据。改进方向：预设增补三机制（标题分散对齐公式/分焦点块引用框/递归
   切分饱满排版）+ 逐页布局规格入预设 + 机械判据扩充。
3. 两项均属可修面；具体方案见 A.a2。

# A.a2 解决方案报告（tb-5 返工第 1 轮）

## 解决方案

### 一、Science 334 官网链路打通（基础设施，a5 实施，devops）

目标：`pysci-research read 10.1126/science.1210713` 能稳定拿到 PDF 全文；失败则给出
可核验的不可行证明。

1. **过 CF 浏览器链路打通**（主修）：`read` 渠道候选序改造——对 CF 保护站（挑战特征
   `Just a moment…`/`challenges.cloudflare.com`），将 **Playwright 真机浏览器通道**
   （browser_fetch.py，能力已在、playwright 已装）提为一等渠道：
   - 打开 DOI 落地页 → 检测挑战页 → **等待 JS 挑战完成**（导航落定/`cf_clearance`
     cookie 出现，超时上限 ~30s）→ 同会话内下载 PDF（校园网机构 SSO 透明，无需登录脚本）；
   - headless 被指纹识别时自动降级 `--headed` 重试一次；
   - PDF 落盘按 DOI 稳定命名，与既有缓存/拾取（`cache find`）兼容。
2. **Science 适配**：`PublisherAdapter` 增 science.org 条目（正文选择器/等待点），
   正文抽取走既有管线。
3. **重试语义**：CF 挑战/超时归「可重试」，N 次指数退避——吸收用户实测的响应不稳定。
4. **兜底**：浏览器链路仍被持续拦截时，试 Zotero「查找可用 PDF」（其内置浏览器栈）；
   全部失败须在报告给出**逐渠道命令+输出**的不可行证明（用户要求：不可能则详细解释）。

### 二、PPT 预设升维（「学院正式汇报预设」修订，b2 前半产出，writing 起草）

按用户批语 1–3 条提炼为预设规则（未来零成本复用）：

1. **标题规格**：页标题分散对齐（algn=dist）、以框长效应实现微字间距；**焦点块胶囊标题
   一律分散对齐**，框宽非线性公式——字符数越少字边距越大（2 字≈1 字宽间距），随字数
   增多每字附加间距递减；公式程序化（`estimate_title_width_in` 扩展为含字间距档位）。
2. **缩略引用文本框改版**：每焦点块一框（不再全页一框）；框左缘与对应焦点块左缘对齐；
   文献 ≤3 条时一行一文献、≥4 条不限；同页多框上缘统一（高度由行数最多的框定），**下缘
   直达页面下缘灰边**。
3. **饱满排版代数**（新增预设章节）：
   - 可排版区域 = 页面 − 顶部标题行（固定高）− 底部引用行（高=max 各框行数）；
   - 递归正交切分（横线/竖线）得子块；多子块同焦点块时**必须同父**（组合 bbox=紧凑父矩形），
     仅左上子块带焦点块标题；
   - 子块三类：文本块（细边框，标题可入左上）/ 单图块（粗边框，纯图）/ 多图块（统一白底
     包多图，内部图宽高比差 ≤1.5:1，可不严格等宽高）；相邻同父单图块并为多图块；
   - 间距两级：焦点块间稍宽、同焦点块子块间稍窄，同级恒定；
   - 饱满技巧：图优先 fig1→实验图→占位符同款，缩放使相邻图等宽/等高→不可行转多图块
     →再不可行加文本块凑饱满矩形；同页焦点块标题尽量上缘/左缘对齐。
4. **机制性保证（组长裁决：规则为主、机械判据为辅）**：
   - 规则面：以上全部写入预设（构造法可照做）；
   - 机械面：扩充 `compose slides geometry`（或新 `slides layout`）判据——①焦点块轮廓
     饱满（bbox 紧凑、无游离元素）②同级间距一致性③引用框左缘对齐与行数规则④焦点块
     标题对齐检查；按实现成本取舍，判据清单随 a5 交付。
5. **逐页布局规格**（批语 4–11 条，b2 版面真源）：p3 沿草稿左中右；p4/p5 左右/左中右且

   或直角）、右单图块；p8/p10 左中右、图与占位一致；p9 左图保留、右图换草稿同款、**补
   PRApplied 25 054054 图（共 3 图）**。
