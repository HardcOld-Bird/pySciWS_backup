```
## 4. 高频查阅维度集中呈现（信息架构硬判据）

**缺陷定式**：交付物按「事项性质」分节是自然写法，而用户实际是**按维度**查阅（时间线 /
地点 / 金额数值 / 待办 / 口径差异 / 责任人）——**高频维度不集中呈现 = 每次查阅都要全文扫读**。
用户 2026-10-15 驳回 tb-20261015-091655-1 原文：「建议补充硬性时间节点章节……建议将所有这些
硬性时间节点集中总结，方便我关注」。凡总结 / 报告 / 综述类交付皆可能重演，与执行者是谁无关。

- **原则（以使用场景为纲）**：交付物组织以用户后续**使用场景**为纲——凡可预判会被
  **反复查询**的维度，必须有**集中章节或索引视图**（时间线就该有专门的时间线章节，
  数值就该有汇总表），不得只按事项性质分节让维度散落。
  原文确实未提供某维度信息时**如实声明**（「原文未提」），不得以省略该节代替。
- **任务书判据化**：总结 / 报告 / 综述类任务书的 `success_criteria` 显式含一条
  「**高频查阅维度集中呈现**（列明该交付的高频维度清单）」。机械可验：抽查清单上每个
  维度在交付物中是否有集中章节 / 索引视图。
- **反推法（设计流程）**：写交付类任务书时先问「**用户拿到后会反复查什么**」，把答案
  写成集中章节清单，落到该任务书的 `success_criteria` 里；维度清单随材料类型走——
  总结类至少覆盖时间（硬性时点 / 截止期），材料含金额 / 地点 / 责任人 / 口径差异者一并列。
```
