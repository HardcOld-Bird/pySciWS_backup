== 一、成因核实（有据；含一条**证伪**）==

**[证伪] 成因 1「同参双实例共存 ≥4 分钟」= venv python 垫片，不是两个看门狗**
现场那对进程实测：`pid 21324` exe=`.venv\Scripts\python.exe`（ppid 9520）→ `pid 4544` exe=`D:\XiGPrograms\uv\python\cpython-3.13.15-windows-x86_64-none\python.exe`（ppid 21324），argv **完全相同**、相隔 7ms；**锁 pid = 4544（子进程）= 真正跑循环的那个**。垫片模型独立复现：`python -c "…"` 一次调用即得两个同 argv 进程。
⇒ 「双生 ≥4 分钟」与「未按 lock_busy 退出」在垫片模型下是**必然读数**：父进程是等待的转发壳，永不调 `acquire_lock`，也没有第二份日志（`20261015-180151.log` 全程只有一行 `[▶] 看门狗启动`）。
⇒ **验收口径 4（wmic 过滤 `_watchdog-loop` 恒 ≤1）按字面无法满足**：一个健康实例恒为 2 个 OS 进程。正确口径见下（已按正确口径通过）。

**[真] 成因 2「start 幂等闸竞态」——实测复现，旧代码并发 start×5 → 派生 5 个**
`watchdog.start_watchdog` 的「查在跑 → 派生」无互斥；子进程从启动到上锁有数十毫秒窗口，期间 5 个调用全部看到「不在跑」：实测回报 5/5「已后台启动」。新代码同场景 → **派生 1 个、4 个回报「已在跑」**。

**[真] 成因 4 的底层通道「acquire_lock 半写载荷窗口」——实测可偷锁**
`os.open(O_EXCL|O_CREAT)` 建成与写 payload 之间文件是**空的**，`read_lock` 把空文件读成 `None`（与损坏锁同路），竞争者据此立刻 `unlink` 即成**偷走仍在写入的活锁** → 两个实例各自以为自己持锁。负控：旧代码在 50ms 放大窗内返回了锁记录（偷锁成功）。
（附带自我纠正：我第一版探针报「并发 5 进程全拿到锁」是**探针缺陷**——子进程拿到锁立即退出，锁成死 pid 残骸被合法接管；改成「拿到后持有 3s」后旧代码即 1/5 ×3 次。**acquire_lock 的常态互斥本身没问题**。）

**[已具备] 成因 3「run_log 同秒撞名」不成立**
`new_run_log` 自 28d5285（2026-10-12）已有 `O_EXCL` 占位 + 顺延：实测同秒 5 次 → `20261015-181751.log / _002 / _003 / _004 / _005`，互不相同。未重复实现，仅补回归用例钉死。
