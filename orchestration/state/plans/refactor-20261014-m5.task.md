## 背景

m4 建好成员队列与 worker。本环节把「完成→通知→组长推进」这条链做成**统一事件层**，
并把 plan 推进从阻塞 run 改为事件驱动的 advance——多 plan 并行自此成为一等能力
（REFACTOR.md §0 核心语义转变）。**向后兼容是硬要求**：`plan run` 现语义不许破坏。

## 目标（四件，缺一不验收）

1. **统一事件流**：`orchestration/state/events.jsonl`（追加式，channel-events 同族）。
   事件类型与发射点：
   - `JOB-DONE`：7 专职+deputy 每件 job 完成（m4 worker 消化处）；
   - `STEP-REVIEW-DONE`：宿主 job+其 reviewer 附属**合并完成**时发**一次**；
   - `QUEUE-EMPTY`：devops / bencher 队列消化完（裁决 ② bencher 归此类）；
   - `TASKBOOK-NEW`：**收编 m3 的最小扩展进本层**（单一实现，不留两份）；
   - `NEEDS-LEADER` / `QUOTA-STOP` / `CHANNEL-STOP` / `CRASH`：沿现制迁入同一流。
   `watch.py` detect 收口上述类型；`orch status` 观察面可读最新事件。
2. **唤醒策略表**（§3.2）：JOB-DONE=每件唤醒组长（7 专职+deputy）；STEP-REVIEW-DONE=
   合并单元一次；QUEUE-EMPTY=devops/bencher 一次；TASKBOOK-NEW=立即；inspector 维持
   自循环仅 NEEDS-LEADER 类唤醒。**合并唤醒（防唤醒风暴，硬规格）**：唤醒是边沿触发，
   组长醒来经 `orch events drain`（或等价命令）**一次排空全部积压事件**再逐 plan 推进；
   多 worker 同时完工折合一次回合。drain 幂等。
3. **plan advance 事件驱动**（§3.5）：
   - `orch plan advance <id>`：把下一环节**入队 m4 成员队列即返回**（任务书延迟书写语义
     保留：advance 时给当前环节任务书）；job 完成事件驱动下一 advance；
   - `plan run` 保留为兼容形态（内部=循环 advance+等待），既有调用与测试不回归；
   - 环节的 review:true → 走 m4 reviewer 附属语义，通知单元= STEP-REVIEW-DONE；
   - **多 plan 并行**：多个 active plan 各自 advance 互不阻塞；同一成员队列 FIFO 串行，
     不同成员即并行；交接处暂停/机械验收 FAIL 回派/blocked 语义保留（事件驱动下由
     组长在 drain 后决策）。
4. **收编与单一实现**：m3 的 TASKBOOK-NEW watch 扩展、m5 新事件，全部走同一 detect/基线
   机制；发现可与 channel-events/queue-complete 判定共用的逻辑抽公共，不复制。
