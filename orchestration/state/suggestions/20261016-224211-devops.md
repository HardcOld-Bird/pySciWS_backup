# backlog 组包与独立入队双记账：组包已消化的建议单又被单独入队，重复烧跳

kind: defect
source: leader
fingerprint: backlog-batch-double-entry-20261016

## 现象（实证，2026-10-16 22:3x devops 队列快照）

建议单 `20261016-215944/-215945/-215946` 三张由组包 job 一次性消化（交付留档 `devops-20261016-220139-20261016-215944-devops.md`，正文显式「backlog id=…-215944, …-215945, …-215946」且三项均已实施、29 测绿、已合并 `8133fdd`）。但同刻 devops 队列里仍有**独立入队的 backlog-batch 条目**在重复排这些单：

```
in_progress | devops-20261016-220824-20261016-215945-devops | backlog-batch
pending     | devops-20261016-221704-20261016-215946-devops | backlog-batch
```

即：计划器组包时把 215945/215946 折进了组包任务书，却又（22:08:24 / 22:17:04，均晚于组包 job 22:01:39 开跑）给它们各自生成了单独队列条目——双记账。后果：每个重复条目烧一跳 devops 容量去「发现已经做完」，还挤占真实工作（polish-b 被排在其后）。对照：`20261016-220500` 的独立条目是**正当**的（组包交付明示「未列入本批菜单，留其自身派发」）——问题只在「组包消化过的 id 未撤销/未标记其独立条目」。

## success_criteria:

- 组包机制双记账根治（任一方向）：① 组包入队时**撤销或标记**其覆盖的 backlog id 对应独立队列条目（若已存在）；或 ② 独立条目入队时**校验**该 id 已被某组包任务书覆盖则跳过；或 ③ worker 取条目时先对账（id 已随组包交付 → 直接销 done 不派跳）；
- 回归测试：构造「组包覆盖 X + X 独立条目在队」场景，断言最终只执行一次（或重复条目被销账、不派生会话）；
- `orch status`/`orch queues list` 的积压读数不把「已组包消化的重复条目」计入待办（口径同步）；
- `uv run --no-sync pytest tests` 全绿。
