**场景**：本会话我连续多跳把「侦察结论 + 落地路径」写在 `<blocked>` 里交付（本单与 `180500` 两例）。这类「**已侦察、未实施**」的 blocked 与「撞上障碍、不知怎么办」的 blocked 在体系里**没有任何机械区分**：drain 的抢救链只看 `<blocked>` 与 `tags`，`orch status` 也只报「谁被挡了」。于是组长要读完正文才知道该条是「等你裁决」还是「等你排期/再派一跳就能落地」——而这两类的最优处置完全不同（补判决 vs 直接重派）。

**易错点**：`<blocked>` 语义过载。现状下它同时承载「环境/权限受阻」「需人类裁决」「执行端余量不足」「上游数据缺失」四类，而 `tags` 词表里只有 `merge_dirty_face` 这一个**会改链路**的标签——其余一律等价。我这次两单卡点类型不同，但对 drain 完全一样：都会被抢救成 `wip(salvage)` + 挂回条目等组长看。

**期望形态**：给 `<blocked>` 增加一个**受控的成因档位**（与 `tags` 同纪律：词表落 `state/failure-tags.json`、gate 校验），例如 `reason=needs_decision | capacity | blocked_by_env | blocked_by_upstream`。前两类让 drain/status 能分列呈现（「待组长裁决 N 条 / 待排期 N 条」），并让链路策略可按档分化（例如 `capacity` 允许立续作单并保面续派，`needs_decision` 则停链等裁决——恰好把本轮 `20261013-102152-devops` 建立的「停链」口径用在对的地方）。

success_criteria: `<blocked>` 可带受控 `reason=` 档位（词表外退回）；`orch status` 与 drain 的 `.done` 按该档位**分列**计数（构造两条不同档位的 blocked → 输出里两档各计 1）；未标注仍合法。
