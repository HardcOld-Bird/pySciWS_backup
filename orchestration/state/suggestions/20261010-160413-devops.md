# 改进建议（devops，待审批）

**缺陷类（本任务调研 premise 被实测部分否证——不影响已落地的尺子，但影响下一步选择）**

用户裁决记录的「Qoder envelope 与 jsonl 逐轮 usage 在双渠道全为 0」中，**token 字段确实全为 0**，但**逐条 credits 与 context_usage_ratio 非零、且双渠道都非零**——精确计量可能不需要估算。证据（只读探针，main 安装码可直接复跑）：

```
cd C:/Users/antar/.qoder-cn/projects && uv run python -c "<递归扫 jsonl 的 message.usage>"
[devops 会话 6f0cc8e5（BYOK qmodel_38max）] usage 条目=222，非零=222
   逐条 credits 合计=67.6949   ctx_ratio 首=0.08242 峰=0.9246 尾=0.7371
   contextWindow=1000000（记录顶层）    input_tokens/output_tokens/cache_* 全为 0
[figure 会话 76757469（内置 qfmodel）]   usage 条目=85，非零=85
   逐条 credits 合计=18.7451  ctx_ratio 峰=0.5200
   同一条款下 envelope total_credits 实测报 0（见台账 ADR 与 §13 2026-10-10 修正条目）
```

三点含义：
1. **内置档并非「不计费」**，只是 envelope 聚合层不上报——逐条 credits 在本地 jsonl 里就有（figure 会话 18.75 credits）。这与「flash=限时免费、零额度消耗」的渠道假设可能冲突，值得核对是否内置免费期也在按条计 credit（若与 2026-10-10 烧穿订阅额度事故同源，属**计费护栏**级别，建议优先转呈用户）。
2. 更准的尺子现成可用：本次已建好「双端测量 + registry 水位」的机制，把 `session_chars` 换成「解析水位区间内新增行的 `credits` 求和 / `ctx_ratio × contextWindow`」即得**测量值**而非估算，且双渠道同法。
3. 若采纳，`delta_chars`/`est_tokens` 可与新列并存一阶段做对照（台账已有原值落盘，改口径不需重跑派发）。

建议：由组长裁定是否开一条 backlog（暂名 `ledger-credits-from-jsonl`），并先把「内置 flash 档是否实际扣 credit」这一问转呈用户——它直接关系到 §3.5 的渠道策略前提。
