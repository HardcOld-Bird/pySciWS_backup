场景：`statecommit.py` 模块 docstring 声明「已跟踪文件的改写仍是普通的 ` M` 面上改动、**交给既有的
state 收尾扫描**」，但这个「state 收尾扫描」在仓里查不到实现：`grep -rn "收尾\|closeout" src/pysci`
零命中（只有 worktree 摘面那几处），`orchestration/guards/` 两个 guard 都不提交 state，README /
leader-only / references 也没有任何角色认领它。后果是运行期改写的**跟踪面**长期滞留在 main 工作区
未提交——本跳实测 main 未提交 **16 项**（含数小时前写的 leader-notes、backlog、plan state），其中
`data/taskbooks/tb-20261015-091655-1.state.json` 与本单改动面相交，`pysci-dev worktree merge` rc=2
拒合并：一单**已完工且全量测试全绿**的改动只能停链等清面，还连带技能部署（sync 须在 main 上做）
也做不了。读那条 docstring 的人（比如我）会以为有安全网，实际没有。
success_criteria:
- `grep -rn "收尾扫描" src/` 的命中处要么指向一个**真存在**的机械提交落点（有实现、可实测：制造
  一次运行期改写跟踪状态面 → 跑一次该落点 → 产生一笔 state 提交），要么该表述已从 `statecommit.py`
  docstring 移除/改写成「由谁在何时提交」；
- 端到端判据：一次运行期改写跟踪状态面后，无需人工 `git commit`，main 的 `git status --porcelain`
  不再长期残留该文件（或文档明确写出提交责任人与时机）。
