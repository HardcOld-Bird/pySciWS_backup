success_criteria：`pysci-dev worktree merge <name>` 在「分支已含 main 全部提交、但 worktree 的 gitignored 运行态比 main 薄」时，仍有一条**不搬运行态**的合并通道（新旗标如 `--no-cp-state`，或自动跳过 cp 并继续 merge），且中止时返回非零 rc 并在 `[NEXT]` 里给出该通道——不再要求使用者绕过工具手敲 `git merge --no-ff`。判据=一次真实孤儿回收单在该形状下能走工具面合并。

**现象**：本单是孤儿条目回收，worktree 建于 16:46、其 `sessions-runtime.json` 只有 1 条会话，main 已有 41 条。工具的会话数自检按设计拒绝 cp（防覆盖更丰富的运行态），但它把 cp 与 merge 捆在同一条路径上，于是**唯一被文档认可的合并面直接堵死**，使用者只能绕过内建交集检查手工 `git merge --no-ff`——而合并顺序、判据、脏面保护恰恰是工具存在的理由。

**证据**
```
$ pysci-dev worktree merge 20261012-164600-leader      # 主树，env -u PYSCI_PROJECT_ROOT
== 合并前交集检查（本次提交面 ∩ main 未提交面）==
  本次提交面 17 文件（merge-base 起算） / main 未提交 6 项
  [√] 交集为空（无关脏项不拦）
[!] worktree 侧会话数 1 < main baseline 41——cp 会覆盖更丰富的 main 运行态、丢会话，中止；
    核对 worktree 是否 stale（应从最新 main 起 worktree add）
```
提示语把责任指向「worktree stale」，但本分支**已先 `git merge main` 同步到尖端**（`26135e3`），代码面一点不比 main 旧——只有 gitignored 运行态薄。按提示重建 worktree 反而要重做全部交付。

**建议形态**：运行态搬运与代码合并解耦——交集检查照做，cp 阶段可跳过（跳过即打印「运行态保留 main 版，未搬」），会话数自检降级为告警而非中止。
