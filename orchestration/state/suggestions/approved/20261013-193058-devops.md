**场景**：`20261013-193500-leader` 的 approved 里有一个**很好的东西**——「组长裁决（devops 点名要的授权）」段，把执行端在上一轮 blocked 里点名的授权（bandwidth 反转熔断、兜底回升 kind 名、outage 不动、unknown 二级判据）一次性写全了。这正是「拆单」应有的形态：拒绝半做的报告 → 组长把授权补齐 → 重派即可执行。

**易错点**：这个形态**只靠人记得写**。approve 时的默认产物是「已入 backlog（第 N 位）」（无附注）——本会话多单都是这个空附注形态；而**带授权的重排**只有组长主动加附注时才有。于是「执行端点名要授权 → 组长补授权」这条闭环，在机械面上没有任何东西提示它发生过：重派的任务书里，授权是叙述文字，既不是可校验字段、也不与当时那份 blocked 报告建立关联（谁点了名、点名要什么、补没补全，只能靠人读上下文）。

**期望形态**：给「因缺裁决/缺授权而 blocked」的条目留一个**可机械追踪的闭环**——例如 blocked 报告里可选带 `needs: decision` 时，drain 把该条挂成「待组长补授权」态并在 `orch status` 单列；重派时任务书自动注入一行「本条为补授权重排：原 blocked 点名了 X/Y/Z，本次已补 A/B（来源：approve 附注）」——或至少让 approve 对这类条目的**空附注**给一句提醒（「该条上轮因缺授权被拒，补授权前重排会再次白烧」）。本会话我有两单正是这类，其中一单靠组长手写附注才闭环、另一单（纯余量）确实无需授权——两者在机械面上长得一样。

success_criteria: 条目带「上轮因缺授权 blocked」标记时，重派任务书含一行「原点名事项 / 本次补齐情况」的对照（可用单测钉：构造该标记 → `backlog_task_text()` 出现该行）；或 approve 对这类条目的空附注给出提醒。
