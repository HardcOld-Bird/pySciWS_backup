# 改进建议（leader，待审批）

**（缺陷类）抢救全自动：崩溃/腰斩场景的未提交进度现为「半自动保住、手动续作」，且崩溃回收会 force-remove 销毁半成品**

kind: defect
背景（用户指令 2026-10-12 23:4x：「希望全自动，不依靠手动处理，以免意外丢失
进度」）。现状实测盘点：
- run_failed 腰斩 → 条目 needs_leader、worktree 保留 ✓（保住面自动）；
- 但续作要组长手动盘点、手动立单（E1/E5a 两次均如此）✗；
- **worker 崩溃孤儿回收**：`git worktree remove --force` + `branch -D`
  （drain.reclaim）——若当时有未提交工作，**自动销毁**，比不抢救更糟 ✗。

修复面（全自动抢救流水线）：
1. **回收先抢救**：`reclaim/cleanup` 前必查 worktree `git status --short` 与
   `main..HEAD`——有未提交/未合并内容 → 自动 `git add -A` 打 **WIP-salvage
   提交**（消息含条目 id 与时间戳）并**保留分支**（不 branch -D）；干净才可
   原样清理。force-remove 仅对确认干净的 worktree 开放；
2. **自动续作单**：条目以 run_failed/needs_leader/crash 收场且其 worktree 有
   WIP 提交或未合并提交 → **自动**注册续作 backlog 条目（source=salvage，
   kind=defect，note 引 worktree 路径+分支+WIP commit，指令=原地续完），
   无需组长手立（组长仅收 watch 事件知会）；
3. 与 #71 的「里程碑提交」charter 纪律互补：代码面 WIP-salvage 是兜底，
   里程碑提交是常态；
4. 与 #76（进程面回收）同族不同面：#76 管进程存活与 sid 占用，本单管
   工作树内容存活——同批施工可，机制独立。

success_criteria：
- 构造「崩溃+脏 worktree」单测：断言 WIP-salvage 提交存在、分支保留、
  自动续作单入队（source=salvage）、下一轮自动被消化续完；
- 构造「干净 worktree」单测：原清理行为不回归；
- 一次真实场景（或 dry 演练）端到端：零组长手动动作，进度零丢失；
  全量无回归。
