# 改进建议（leader，待审批）

**（缺陷类）bencher 副本 A/B 空壳完成：副本就绪后未派发案运行即标 done，无二元判决落账**

kind: defect
复现（实测 2026-10-12，main c814a1b，bencher 通道）：
```
orch bench-add capture --cases fig-basic --start   # ✓ 正常：manifest+4 文件归档
orch bench-add ab --ref-a b2e5b358 --ref-b 89a93c3 --cases fig-basic --start
```
实际输出（run 165247 全 log）：两副本「就绪→还原归档 4 文件」后**立即**
「副本清理」，worker 结束 `耗时 1.3s`，done items
`{kind:"ab", status:"done", elapsed_s:1.3}`——
- 无任何 `_hop`/派发记录（对照 run 144741 真跑两案用时 139s）；
- `state/ledger/evals.jsonl` 无新增判决行（最后仍是 14:50 的 runner=bencher 两行）；
- status「待查看」面与 .done 均无「改善/未改善」读数。

期望输出：A/B 必须在两副本各跑案内案（minimum 档真实 headless 派发）→ 对比
指标与判决 → 二元判决（改善/未改善，或按 E4 规格先「无基线可比」明确
inconclusive）落 evals.jsonl（含 a/b 两侧行）→ done 摘要携带判决值。

危害定性：这正是 REFACTOR §14 要防的「静默完成」形状——done 无判决 = 把
「没做」伪装成「做了且成功」，比 blocked 危险；组长按 done 销账即漏单。
（对照：窗口污染护栏在 145147 上的行为是正确的——inconclusive+留痕；本单是
「无事发生也 done」。）

修复面：
1. `bench ab` 执行路径核查：副本就绪后到清理之间缺失的案运行调用定位
   （疑似分支/参数错误致 cases 解析为空即跳过——`--cases fig-basic` 显式给
   了案，1.3s 内完成说明连「无案可跑」的告警都没触发）；
2. **done 语义收紧（机械判据）**：ab/capture/run 三类队列项，done 必须携带
   判决或读数证据（ab→evals.jsonl 新行 id 或 inconclusive+理由；capture→
   归档文件数>0；run→判决行）；无证据不得标 done，一律 failed 并计入
   「累计失败」提示面；
3. 阳性回归测试：a) 空 cases 的 ab 必 failed 不 done；b) mock 派发通路验证
   ab 全流程产生判决行；c) 现有 run/capture 用例不回归。

success_criteria：
- 真实重跑「fig-basic A/B（相邻提交对 b2e5b358→89a93c3）」→ 两副本各真跑
  （台账各新增一行 runner=bencher kind=ab 读数）→ 输出二元判决或
  inconclusive+窗口证据，二者必居其一，绝无 1.3s-done-无判决形状；
- done-无证据→failed 的机械判据单测全绿；全量无回归。
