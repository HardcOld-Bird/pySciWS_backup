# 改进建议（leader，待审批）

**（缺陷类，附证据）watch QUEUE-COMPLETE 对 run 完成事件脱靶，且基线推进把账吞死（status 补账同哑）**

kind: defect

复现与证据（实测 2026-10-11）：
- 21:05:57 drain run 20261011-210557 启动；21:06:36 watch 挂载（armed_at 可见
  state/watch.json）；21:42:41.77 `.done` 落盘、锁释放（drain 代码顺序
  release_lock→write .done，log 时间戳吻合）；
- 挂载的 watch 进程持续轮询（polls 44→57、心跳每 ~60s 新鲜），但整场
  fired=[]、后台任务输出文件为空——**QUEUE-COMPLETE 从未命中**；
- 其后 `orch status` 补账段显示「自上次基线以来无新事件」——因每轮
  `prev=cur` 无条件推进基线，done 名进入基线那一轮即被永久吞账，**补账同哑**；
- 对照实验排除法：同一部署代码重放 detect_events（running+旧done →
  idle+新done）命中 QUEUE-COMPLETE；前台挂载中投喂 .done（14s 窗口）命中；
  E0 合并未改 watch.py/drain.py（`git diff 7817e0e..HEAD` 该二文件为空）。
  ⇒ 检测纯逻辑正确，故障在**实轮询的某帧把 done 名吞进基线而未发事件**。
- 候选瞬态机制（按代码路径列出，修复时须逐一排查并加诊断）：
  ① `same_run` 抑制帧：某轮询恰见「锁仍 running（pid 被 Windows 回收给新进程
  判活 / 锁文件释放 unlink 因共享读句柄失败残留）」且 lock_run==done 名——
  该帧抑制后基线照样推进，此后 done 名不再变化，事件永久丢失；
  ② `.done` 半写态：轮询恰在 write_text 中途读到 JSON 不完整 → latest_done
  返回 None → cur.done=""（本轮不报但把基线推到空串，下轮应能报——若下轮
  恰又叠加 ① 则同样吞死）；
  ③ 其他未识别瞬态——**现无留痕无法定案，这是本缺陷的可诊断性部分**。

修复要求（识别强化 + 抑制帧不吞账 + 留痕）：
1. QUEUE-COMPLETE 身份从「done 名变化」强化为 **(done 名, completed 时间戳,
   count) 三元组**：三元组任一变化且锁非 running-该-run → 报；同 run 的 .done
   被重写（如配额/协作停止后续跑完）也能再报。
2. **锁 running→idle 转移帧**：若该 idle 帧存在对应 run 的 .done 而该 run 从未
   报过完成 → 必须报（覆盖 ① 的瞬态）。
3. **抑制/跳过帧不得推进基线**：detect 判定「有完成事实但因 same_run 等瞬态
   抑制」时，base 保持原值或记 pending-complete 标记，下一帧再判。
4. 黑匣子：watch.json 增 `recent` 环形缓冲（最近 ~10 帧：ts、lock_state、
   lock_run、done、抑制原因），命中/超时/异常退出写 `exit_reason`；进程被
   外部杀死时下次挂载/status 能读出「上一任遗言」。
5. 单测覆盖：pid 复用假象（锁存在 pid 判活为真 + done 已存在）、.done 半写、
   同 run .done 重写、running→idle 转移帧报完成。
6. 组长侧操作纪律补一句（orchestration 技能真本）：**测试/诊断性挂载 watch
   前须确认无 live 挂载或先停**（arm() 全局单例覆写 watch.json，本次排查曾
   被两次测试挂载干扰判读）。

success_criteria：
- 上述 5 类单测全绿（tests/skills/orchestration/test_watch_*.py）；
- 一次真实多批次 drain run：watch 命中 QUEUE-COMPLETE 单行唤醒 + 组长收到
  后台任务通知；若再脱靶，黑匣子 recent 足以定位抑制帧原因。
