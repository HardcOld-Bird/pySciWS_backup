# 改进建议（devops，待审批）

kind: usability
delivery: leader-reflection
来源：组长工作摩擦反思（用户指令立单 2026-10-15，第二轮）

**场景**：①若干真实存在的顶层命令未进任何文档面；②建议单的「重复/合并」处置无口径，
`resolve` 的实际作用域与其名字的直觉不符，组长只能临场猜测。

**证据（复现 → 实际 → 期望）**：
- 复现①：grep `requeue|resolve|drain-stop|twin-review|refresh-models` 于
  `.qoder/skills/orchestration/SKILL.md`、`references/command-surface.md`、
  `orchestration/README.md` —— **零命中**（`watchdog` 命中均为机制描述，非该命令）。
  这些命令只在 argparse usage 行里出现过一次（因别的报错偶然看到）。
- 复现②：I.i3 交付携带的建议单 `20261015-204145-reviewer` 与我同日立的
  `20261015-204911/204912` 四点完全重合，需要「重复单合并销账」处置。`pysci-orch resolve
  -h` 实测其作用域=「backlog 条目且 status=needs_leader」，不含建议单；最终只能
  `reject --override` 写明去重——但 reject 在历史面上呈现为「已否决」，与「内容已采纳
  （经另两单）」的事实语义相反，审计时易误读。
- 另注：建议单文件名后缀语义不一——成员交付生成的 `<ts>-<member>.md` 是**来源**成员，
  组长代补时后缀实为**目标**成员（我写 `-devops`），`suggestions` 列表的 `[member]` 列
  不区分二者。
- 期望：命令面文档完整；重复单有语义正确的处置口径。

**建议**：
1. command-surface.md 补全顶层命令清单（至少 `requeue`/`resolve`/`watchdog`/
  `twin-review`/`refresh-models`/`drain-stop`，各配一行语义与作用域）；
2. 建议单「重复/合并」处置三选一：`resolve` 扩展接受 suggestion id（销账+--note 留痕）、
  或 `reject` 加 `--as-duplicate <ids>` 旗标（历史面呈现为「合并至 …」）、或文档明确
  「重复单=reject --override 写明去重」为既定做法（成本最低，但历史面语义仍反）；
3. 顺带在建议单格式文档（见 20261015-202600-devops 单）注明文件名后缀=来源成员、
  组长代补时后缀取目标成员的现状与显示口径。

success_criteria:
- 五个顶层命令在 command-surface.md 各有一行语义（grep 逐一命中）；
- 重复建议单有一种文档化处置，其历史面呈现不再与「内容已采纳」相矛盾（或文档明确
  接受 reject 口径并说明审计读法）；
- `suggestions` 列表对组长代补单的 `[member]` 显示口径有注明。
