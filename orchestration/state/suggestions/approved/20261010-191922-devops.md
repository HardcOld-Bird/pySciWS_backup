# 改进建议（devops，待审批）

**机械生成/改写 `orchestration/skills/**` 下 markdown 时，首次提交必被 pre-commit 的 `end-of-file-fixer` 改写而失败**，任何「脚本产出技能文档」的任务都会撞上：钩子报 `Fixing <file>` 后中止提交，改动留在工作区，必须重新 `git add` 再提交一次。

- 复现：worktree 内 `git add orchestration/skills/<5 个技能> && git commit -m '…'` → 输出 13+ 行 `Fixing …`，`git log` 无新提交，`git status` 呈 `AM`（已暂存又被工作区修改）。
- 实际后果：本次拆分**先**做了「分册拼接 == 原文逐字节相等」的验证，**后**提交；钩子削掉 26 个分册末尾空白行后，那条逐字节断言就不再成立（内容仍无损），验证与提交之间存在一个「被钩子改写过、验证已过期」的窗口。若当时直接交付第一次验证的结论，报告的就是一个不再为真的证据。
- 期望：这类任务的正确次序应固化为「生成 → 提交（允许失败一次）→ re-add → 再提交 → 在**最终字节**上跑内容等价性验证」。建议在 devops 技能真本的「worktree 作业规程」或「技能部署」小节补一条：**任何脚本批量产出 `.md` 真本时，必须在钩子改写完的文件上重跑内容校验，不要在生成后立即校验就交付**。我这次是在事后补了校验，运气好而已。
