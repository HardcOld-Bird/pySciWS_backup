# 建议单格式与解析器不一致：`success_criteria`「段」措辞认不出，首写必踩坑

kind: usability
source: leader
fingerprint: suggestion-criteria-format-doc-20261016

## 现象（实证）

2026-10-16 立单 `20261016-203600-devops` 时，按 `references/command-surface.md` 的「正文须含 `kind: defect|usability` 与 `success_criteria:` **段**」写成 markdown 标题段 `## success_criteria:`，`approve` 被拒：

> [!] 建议 …（kind=defect）缺可证伪成功判据，拒绝入队。**先对盘**：判据可能只是写成了解析器读不到的形态。接受的书写形态（任一）：· `success_criteria: …`（行首）· `- success_criteria: …` · `**success_criteria**: …` 且判据正文＝标记行之后的连续非空行

即：文档说「段」（读者自然理解为 markdown 标题段），解析器只认「行首标记行＋连续非空行」，`## success_criteria:` 标题形态**不认**。首写建议单必踩、返工一轮（报错文案本身倒是写得清楚——问题在事前无样例）。

## 根因

`command-surface.md` 立单块与 SKILL 速查只有一句话描述，**无最小合规样例**；且「段」的措辞与解析器接受形态不对齐（解析器清单未进文档，文档措辞未进解析器报错）。

success_criteria:
- `command-surface.md` 立单块补一段**可整体复制的最小合规样例**（含 `kind:` 行、`source:`/`fingerprint:` 行、`success_criteria:` 行首标记＋紧随判据行、≥40 字实质正文），并注明「`## success_criteria` 等 markdown 标题形态不被解析器认（或已被认——以实现为准写清）」；
- 解析器二选一：兼容 `## success_criteria` 标题段形态；或保持只认行首形态但在文档与报错文案**明说不支持 markdown 标题形态**（报错已列接受形态，文档与之互相引用）；
- 解析器单测钉住「接受形态清单」（每种可接受形态一条正例＋markdown 标题形态一条按定案断言）；
- `uv run --no-sync pytest tests` 全绿。
