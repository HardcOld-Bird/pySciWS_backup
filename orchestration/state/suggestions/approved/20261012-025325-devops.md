# 改进建议（devops，待审批）

kind: defect

**属性值里出现 `>` 会静默截断交付块，正文与产物路径被污染且不报任何错**

场景：交付块属性面正则一律用 `[^>]*` 界定（`_RESULT_RE`/`_BLOCKED_RE`/`_ARTIFACT_RE` 三条同形，delivery-gate 的 Node 侧疑似同源，需一并查）。若成员在 `reason=` / `check=` 的值里写了 `>`（例：比较符号、`a > b`、数学式、HTML 片段），`[^>]*` 会在引号内部提前停下，剩余部分被当正文起点。

复现（main，commit 5951c28）：

    PYTHONUTF8=1 .venv/Scripts/python.exe -c "
    from pysci.skills.orchestration.tools import delivery as D
    for t in ['<result reason=\"x > y\">正文 B</result>',
              '<result>内嵌 <artifact check=\"none\" reason=\"优于 > 阈值\">p/q.pdf</artifact></result>']:
        d = D.parse_delivery(t); print(d.kind, repr(d.body[:60]), [(a.path,a.check,a.reason) for a in d.artifacts], repr(d.warning))
    "

实际输出：

    result 'y">正文 B' [] ''
    result '内嵌 <artifact check="none" reason="优于 > 阈值">p/q.pdf</artifact' [('阈值">p/q.pdf', 'none', '')]

期望输出：第二条 artifact 的 path 应为 `p/q.pdf`、reason 应为 `优于 > 阈值`；第一例正文应为 `正文 B`。

危害：kind 仍判 result、`warning` 仍为空（严格面「匹配上了」，兜底面不触发，本次告警面救不了它），机械验收却会去 check 一个不存在的路径 `阈值">p/q.pdf` → 报成产物缺失，或更糟：静默略过。比 parse_error 更隐蔽，因为台账上一切正常。

success_criteria：
- 交付块属性面改为**引号感知**扫描（值内的 `>` 不截断），上述两条输入解析出 path=`p/q.pdf`、reason=`优于 > 阈值`、正文=`正文 B`；
- delivery-gate（Node 侧）同形正则一并核对，两侧对同一交付读数一致；
- 新增阳性用例覆盖「属性值含 `>`」「属性值含 `</`」两种畸形，并证明未匹配形态仍走 parse_error/warning 面（不与本次兜底面语义打架）。
