**（E3-prep，REFACTOR v1.0 §4）仲裁团代码面先行：jury 共享库 + orch 封装 + jury-brief 草案（mock 全覆盖，真实连通留用户 Key）**

kind: usability
success_criteria: 见文末判据。背景与授权：REFACTOR v1.0 定稿 + 委托 §15。
**委托期边界**：SiliconFlow API Key 只能由用户本人提供（账号与付费面）——
本单实装全部代码面与 mock 测试，真实连通做成「环境变量就位即用」，缺 Key
走明确降级；用户早晨给 Key 后一条命令即可验收。

规格：
1. `src/pysci/skills/orchestration/tools/jury.py`（共享库，§0.9：不建独立
   CLI）：OpenAI 兼容客户端（base_url 可配，默认
   `https://api.siliconflow.cn/v1`），Key 读环境变量
   `SILICONFLOW_API_KEY`；评审团型号清单配置 `registry.jury.panel`
   （默认空 + 注释：非 Qwen 系硬规则、选型由用户定，代码只校验不含 qwen
   字样型号）；并发调用；结构化输出约束（选 A/B+理由+置信度，强制 JSON）。
2. **双序 + 多数 + 回退识别**（承 §4 与 220622 的收尾证据思想）：每裁判
   A/B 与 B/A 各一次，不一致记 inconclusive 不计票；计票少数服从多数；
   平票/inconclusive 过半 → `escalate=twin` 标记（E6 twin 未上线前挂起呈
   组长——220622 建议里已定此过渡）。
3. 案卷组装：输入 case 文件（两选项全文+证据）→ CLI **自动附加确定性
   材料**（`git diff`/`git log --oneline -5`/涉事文件字节读数/相关台账行，
   按 case 头部声明的目标路径抓取）；案卷全文哈希入档（材料冻结，供审计
   与「裁决被事后证据推翻」回访触发条件计数）。
4. 留痕：`state/evals/jury/<case-id>.json`（问题、材料哈希、各裁判原始
   输出、双序一致性、计票、最终裁决或 escalate、usage、成本）。
5. `orch jury <case-file> [--dry]`：阻塞执行（超时 5 min → 重试一次 →
   仍败该案写 `state/evals/jury-queue/` 待重裁并单行提示，不 raise）；
   `--dry` 只组卷打印案卷不调 API。
6. `state/evals/jury-brief.md` **草案 v1**（组长起草；护栏级——正式生效
   留用户早晨确认，未确认前 orch jury 运行时警告「简报未批准」但可用）：
   含项目优化面/既有裁决约束/「仅涉自身基建直通」规则（§4 用户已确认）。
7. Key 安全：任何日志/留痕不得含 Key；`pysci-dev doctor` 增哨兵扫描 git
   跟踪文件中疑似 API Key 模式（承 §14）。
8. 单测：mock transport 全链路（双序一致/单裁判不一致剔票/多数裁决/平票
   escalate/超时入队/缺 Key 降级/材料哈希冻结/非 Qwen 型号校验）。

success_criteria：
- 上述 mock 单测全绿且入 `orch-tests` 检查面；
- `orch jury --dry` 对示例案卷输出完整组装材料（含自动附加段与哈希）；
- 缺 `SILICONFLOW_API_KEY` 时真实调用路径打印可读降级并入队，不崩不烧；
- doctor Key 泄漏哨兵对构造假 Key 报 ✗、干净树报绿（阳性用例）；
- jury-brief 草案落盘并标注「待用户确认」；全量套件无回归。
