# 改进建议（devops，待审批）

kind: defect

kind: defect
success_criteria：构造一条 kind 非法的 infra 交付，`orch ledger` 该行不再显示「建议✓」（或改为「建议✗未入库」），且 `orch suggestions` 计数与台账读数一致；新增测试钉住「台账建议字段 ⟺ 队列存在条目」同真同假。

**现象**：收口后非法 kind 的提案在入库面被拒（`_persist_suggestion()` 返回空串、不写文件），但台账仍按解析结果记 `infra_suggestion=true`，`orch ledger` 该行渲染「建议✓」。于是出现**两个都为真却互相矛盾的读数**：台账说这一跳提过案、队列里没有任何条目。组长按台账销账会漏单，按队列统计会误判组员没提。

**证据**（main 上，修复后代码）：
```
$ PYTHONPATH=. uv run python -c "from pysci.skills.orchestration.tools.dispatch import _persist_suggestion; \
  print(repr(_persist_suggestion('devops','正文','defusability-placeholder')))"
[!] 改进建议未入库（devops）：kind='defusability-placeholder' 不在受控词表（defect|usability）…
''
```
返回值被丢弃、不入库，而 dispatch 记账路径使用的仍是 `delivery.infra_suggestion` 布尔量，未接收 `_persist_suggestion` 的结果；因此 ledger 行与 suggestions 目录在此形状下必然分裂。

**为什么值得单独修**：本次的教训正是「一处判定、多处读数」——词表校验收口后，如果台账这个观测面不跟着改口径，等于把「静默丢弃」从解析器搬到了记账器，只是这次留下了告警行。机械验收应判「入库成功」而非「组员声明过」。
