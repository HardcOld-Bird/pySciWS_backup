# 改进建议（devops，待审批）

**（缺陷类，附证据）guard 的 fail-open 会静默吞掉 guard 自己的 bug——「全绿」不代表在执法。**

- 复现：首版 `delivery-gate.mjs` 把执行流写在 ESM 顶层 `const size/mdIn/subDirs = …` **之前**（函数声明会提升，但 `const` 有 TDZ），`budgetProblems()` 里第一次触碰 `size` 就抛 `ReferenceError`，被外层 `catch { /* fail-open */ }` 吞掉 ⇒ 一律 exit 0。
- 实际输出：13 例应拦的违规全部 `assert 0 == 2` 失败——是我**先写了 pytest 直跑真 guard** 才看见的；只看「手动喂一个超大 AGENTS.md、exit code 是 0」或 `pysci-dev doctor` 都会误判成"门禁正常"。期望输出：exit 2 + 整改指令。
- 结构性风险：这条纪律不只影响 delivery-gate，`pod-guard.mjs` 同款 fail-open。任何 guard 的 fail-open 都必须配「**违规必拦截**」的阳性用例（负向用例证明"正常时不拦"），否则 fail-open 让 guard 退化成一个静默的空壳，而它的存在本身会让人放松对预算的注意力。我在 devops 技能「guards 面」小节和 AGENTS.md 都写了这条，但**约定不等于机制**。
- 建议：把 `tests/skills/orchestration/test_delivery_gate_budget.py` 这种「node 跑真 guard」的模式登记为 guards 的验收面（新写或改 `orchestration/guards/*.mjs` 时必须有对应的阳性用例），并考虑纳入 README §9 guards 条目——该处属门禁策略条款，我按 charter 不自改，请组长转呈。

**（难用类，一处遗留缺口）组员侧常驻暴露税目前只在"交付那一刻"被检查。**
gate 在 Stop 时测 pod 自建 rules/skills 的 description 合计，但 `pysci-dev doctor` 的常驻暴露档只统计**真本侧** 9 条 SKILL.md description；也就是说，一个组员会话若中途死掉/被回收而从未走到 Stop，他那本 description 账就没人看过，下一轮派发时它已经每跳进上下文了。场景不罕见（本轮 drain 队列里就有 rc=1 中断重跑）。建议下一轮给 doctor 增一项「逐 pod 自建 rules/skills description 合计」报告（三档审计的自然补齐，纯只读，无风险），把常驻暴露税的观测面从"交付时"扩到"巡检时"。
