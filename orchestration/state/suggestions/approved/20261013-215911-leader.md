# 改进建议（leader，待审批）

kind: usability

**来源**：用户提案（2026-10-13）——「devops 的常用功能该整理并硬化进它的基础设施；每次工作正常结束后自动提交并 push」。

**场景（本会话实证）**：devops 的「收尾动作」多是软纪律或半自动，导致遗留：

① **worktree 不自动收尾**：`pysci-dev worktree remove`（摘目录 + 删分支）**已存在**，但 `worktree merge` 成功后**不调用它**——每次正常完成的工作都在 `.qoder/worktrees/` 留一个冗余面（现存 7 个：`20261012-120002`、`20261012-164600`、`20261013-072000`、`20261013-093000`、`20261013-101105`、`20261013-101705`、`20261013-143000`）。**关键区分缺失**：对**已完成**（已 merge，内容在 main）的面，清理是安全的；只有**未完成**（崩溃/blocked）才需保留供抢救链。现状不区分、一律留。

② **提交+推送是 best-effort**：charter 只写「commit 后尝试一次限时 push（`timeout 25 git push origin main`，best-effort，失败忽略）」。`timeout` 在 Git Bash / Windows 下语义存疑（MSYS coreutils `timeout` vs Windows `timeout`）；best-effort 意味着**成功完成的工作可能静默地没被推送**。

**期望形态**：
- ① `worktree merge` **成功收尾时自动** remove worktree + 删分支（失败 / blocked 路径保留，供抢救）；另补一条 `pysci-dev worktree clean`——列出并清理**已合并且冗余**的遗留面，**未合并的拒绝并列出**（先查 dry-run 清单，再 `--apply`）。
- ② 把「成功结束 → 确定性 commit + push」**硬化**（不再是 best-effort）：核对 `timeout` 跨平台可用性（必要时改 Python 侧带超时的 subprocess），push 失败须**明确留痕**而非静默。
- ③ 顺带把 devops 的日常收尾面（worktree 生命周期 / commit-push / sync 后提交台账）整理进 devops 技能的 references，让 flash 档也能照做。

success_criteria:
- `worktree merge` 成功后该 worktree 与分支不再残留（实测：建→改→merge→`worktree list` 不含该面）；失败 / blocked 路径仍保留；
- `pysci-dev worktree clean` 能列出并清理已合并的遗留、**拒绝**未合并的（阳性 / 阴性用例各一，未合并者退出码非 0 并列名）；
- 成功结束后的 commit+push 为**确定性**步骤：push 成功 / 失败均有台账或日志留痕（伪 remote 单测钉「失败不静默」）。
