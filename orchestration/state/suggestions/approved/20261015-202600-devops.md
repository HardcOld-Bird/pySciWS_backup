# 改进建议（devops，待审批）

kind: usability
delivery: leader-reflection
来源：组长工作摩擦反思（用户指令立单 2026-10-15）

**场景**：两处编排语义只存在于「单行提及/源码 docstring」，技能面查不到，影响组长
决策表达：① `review: true` 的机械语义；② 组长立单（手写 suggestions/）入口。

**证据（复现 → 实际 → 期望）**：
- 复现①：grep `review: true|review:true|--review` 于技能 references/ 与 README——仅
  2 命中：command-surface「queues enqueue … [--review]」一行、plan-decomposition §6
  「review: true 标记重炮审查（默认不发起）」一句。**标记后发生什么**（是否自动跑
  `orch review` 审查链/FAIL 自动回派返工/复审升级仲裁）、与 `member: reviewer` 叶子、
  `orch review` 命令三者关系均无文档。本轮 tb-3 需要 reviewer 视觉审核，无法评估
  `review: true` 能否表达，被迫改用 `member: reviewer` 独立叶子绕行。
- 复现②：本轮需组长立单，command-surface 无「suggest/立单」命令（suggestions 只读、
  approve/reject 需已有单）；最终读源码才找到 `workflow.py:1089` docstring「组长代补、
  自动立案、手写文件都会直接落进 suggestions/」——手写文件是认可入口，但格式
  （kind: defect|usability、success_criteria 段、命名 `<ts>-<member>.md`）只在代码与
  历史文件里。
- 期望：两处语义在 SKILL/command-surface 一跳可查。

**建议**：①command-surface 或 dispatch-playbook 补一小节「三种审查表达」：`review:
true` 叶子标记（触发条件与审查链行为）vs `member: reviewer` 叶子 vs `orch review`
命令（何时用哪个）；②同处补「组长立单」：手写 `suggestions/<ts>-<member>.md` 的格式
（必须含 `kind:` 与 `success_criteria:`，正文实质字数下限）与 approve → backlog 后续流。

success_criteria:
- 文档含「三种审查表达」对照（触发/行为/适用场景），review:true 的机械行为描述与
  实现一致（以 dispatch.py 实测为准核对过）。
- 文档含「组长立单」格式说明，照其格式手写的建议单在 `orch suggestions` 列出且无
  `[]` 质检标记。
