**（缺陷类）墓碑自身也写不进时，锁面仍报假 running——判活未采纳「该 run 已有 `.done`」这条收尾硬证据**

E3 修好后仍留一格：`_overwrite_lock()` 两条路（`os.replace`／截断重写）都被拒时（他方以不共享写的方式持句柄），锁记录原地保持 `{pid: 活着, started: 新鲜}`，`lock_status()` 照样 `state=running`，下一任 `acquire_lock` 仍返回 None → 队列被挡到 `LOCK_STALE_S` 6h。此时唯一痕迹是那行 `[!] … released 标记亦写入失败`。实测复现（只读 tmp 锁面，2026-10-11）：

```
cd <main> && PYTHONUTF8=1 python -c "  # drain.LOCK_PATH 指 tmp；os.unlink 抛 OSError(32)；drain._overwrite_lock → False
release_lock -> False
lock_status  -> {"state": "running", "pid": 26784, "started": "2026-10-11T23:11:48+08:00", "run_log": "x.log", "age_s": 0.6}
期望: state != running（该 run 已有 .done = 收尾硬证据）
日志   -> [23:11:48] [!] 锁释放失败（共享句柄），released 标记亦写入失败（残骸待超龄解套）：[Errno 32] sharing violation
```
（期望值有实锤依据：`.done` 由 drain 在 `release_lock` **之后**写出，锁自称在跑却已有该 run 的 `.done`，只可能是残骸——README §4.5 已把这条定为「收尾事实优先于锁的自称」，目前只在观察面执法。）

修复面：
1. `_lock_live()` 追加否决项：锁的 run 已有对应 `.done` → 判非活（与 released 墓碑并列的第二个「已宣告收尾」证据），`acquire_lock` 遂接管；
2. `lock_status()` 该分支给独立读数（建议 `state=stale` + `residue="done-exists"` + `crashed=False`），`orch status` 文案与「残留已标记」并列，避免误读成「pid 已死」；
3. **需同步复核 E2 观察面契约**：`test_watch_complete_identity.py::test_running_to_idle_transition_reports_completion` 的前提是「种了 `.done` 后快照仍读 running」，锁面一旦采纳该否决，该用例与 `detect()` 的 `_in_progress()` 抑制支需一并重述（这正是我没有顺手改的原因——它会改动刚交付的 220622 契约，超出本次批准面）。

success_criteria:
- 新增阳性测试：`os.unlink` 与 `_overwrite_lock` 双双失败 + 该 run 存在 `.done` → `lock_status()["state"] != "running"` 且 `acquire_lock` 成功接管；
- 现有 E2 watch 全套（含 transition 帧用例）在新语义下重述后全绿，全量套件无回归；
- 真实 drain 收尾一次：`orch status` 与 `git status` 均不出现「锁 running 而该 run 已有 `.done`」矛盾态（即 E3 未竟的那条判据被代码面而非运气封死）。
