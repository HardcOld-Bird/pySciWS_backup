**交付协议扩展缺「解析器版本」自适配兜底：合并后的当次派发用新属性交付会被判 parse_error**

场景：E1 给 `<blocked>` 加了 `tags` 属性，同时把 delivery-gate 与 `_extract` 都放宽成属性感知；但派发/审批进程在合并前启动，进程里 import 的还是旧解析器。旧代码：

```
$ git show 636c4a8:src/pysci/skills/orchestration/tools/delivery.py | sed -n '/def _extract/,+3p'
    m = re.search(rf"<{tag}>(?P<body>.*?)</{tag}>", text, re.DOTALL)   # 不认属性
```

后果实测口径：带属性交付 → `kind="parse_error"` → `dispatch.py:67` 定义 code=2 → drain「仅种子 needs_leader」，组包项不销账；组员白跑一跳，且失败原因显示成「交付格式解析失败」而非真问题，排查成本高（这正是我自己下一跳会踩的坑，所以本次刻意不带 tags）。协议类改动以后每次都会有这个窗口（E5 判决包、reviewer 面还会再来）。

建议（轻量，不必新抽象）：`parse_delivery` 在「两者皆缺」判 parse_error 前，先宽松扫一遍带属性形态的 `<result\b[^>]*>`/`<blocked\b[^>]*>`；若宽松扫到而严格没扫到，就按宽松结果解析并在 outcome 里附一行告警「解析器早于协议，建议重跑本单」。这样协议扩展当次就能用新属性，不必等下一跳。

success_criteria: 构造 `"<blocked tags=\"quota\">x</blocked>"` 喂给**旧式严格** `_extract` 的等价路径（可用 monkeypatch 保留旧正则）时，`parse_delivery` 仍返回 `kind=="blocked"` 且 `tags==["quota"]`，并打出一行「解析器早于协议」告警；现有 parse_error 用例（两者皆缺、块并存）行为不变；`orch-tests` 与全量套件无回归。
