# 改进建议（devops，待审批）

kind: defect

**（缺陷类）`release_lock` 的 unlink 失败被静默吞掉，锁残骸能把队列阻塞 6 小时**

kind: defect

证据（实测 2026-10-11，与 20261011-220622-leader 同源）：
- `drain.py:197-200`：`os.unlink(str(LOCK_PATH))` 外裹 `except OSError: pass`——Windows 上他方仍持有该文件的读句柄时 DeleteFile 报共享冲突，**失败无任何痕迹**（run 日志里没有一行）；
- 后果不止观察面误判：`_lock_live()`（drain.py:148-155）在 `_pid_alive` 误真时把残骸判为活锁，`acquire_lock` 遂返回 None（drain.py:172-173）→ 下一个 drain **skipped=lock_busy**，最长要到 `LOCK_STALE_S=6h` 超龄或 pid 恰好被判死才解套——观察面（watch）本条已改为「读穿谎话」，**锁面仍在骗人**；
- `_pid_alive` 的保守判活（超时/OSError → True，drain.py:114-116）与 Windows pid 回收使误真可复现（basic.md §3 记录过 tasklist 误判先例）。

修复面：
1. `release_lock` 失败不可静默：unlink 抛错时把锁记录**改写为已释放标记**（如 `{"released": true, pid, run_log, released_at}`，原子写），并在 run 日志打一行 `[!] 锁释放失败（共享句柄），已写 released 标记`；
2. `_lock_live`/`lock_status` 认该标记：`released` 为真即视为非活锁（接管/清理），`orch status` 呈现「残留已标记」而非「running」；
3. 阳性测试（`tests/skills/orchestration/test_drain_release_lock.py`）：monkeypatch `os.unlink` 抛 `PermissionError` → 断言 (a) 日志含 `[!]` 行，(b) 随后 `lock_status()["state"] != "running"`，(c) 随后 `acquire_lock` 成功接管；并保留「unlink 成功」的旧路径断言。

success_criteria:
- 上述三条阳性测试全绿；一次真实 drain 收尾后 `git status` 与 `orch status` 不再出现「锁显示 running 而该 run 已有 .done」的矛盾态；后续 run 不因残骸被 lock_busy 跳过。
