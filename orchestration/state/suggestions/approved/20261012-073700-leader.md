# 改进建议（leader，待审批）

**（P0-即时，委托期自主裁决）devops max_turns 80→150 + watch 挂载文案硬化 + status 补账覆盖 fired 未读**

kind: defect
背景与证据（实测 2026-10-12 夜航）：
- run_failed(tool_use) 三连（00:04/01:38/03:29，ledger `num_turns` 恒 **80**）：
  大单（E2/E6-prep，多部分规格）在 flash 档下 80 轮必然腰斩——非规格障碍，
  纯编排参数与任务粒度失配；且 drain 组包把两张大单并一批（+1）加剧；
- 组长把 watch 以 `&` 内嵌进其他后台命令挂载（违规：应作 run_in_background
  顶层单命令）→ 事件命中但唤醒通道随父任务终结而断，夜航停摆 6 小时无事件
  送达（watch 侧 fired 留痕完整，属操作面软肋被踩穿）；
- status 补账逻辑只报「基线以来未消费事件」；watch 命中自杀式退出（fired
  已写但唤醒丢失）后这些事件永不补报——status 的「上次运行已结束（event）」
  一行无明细，组长晨间才靠人工翻 fired 发现。

修复面：
1. registry.members.devops.max_turns 80→**150**（timeout 维持 10800）；在
   registry 该成员条目加参数注记（夜航证据：80 腰斩三连）。
2. `watch.mount_lines()` 文案追加一行硬警示：**「必须作为后台 Bash 调用的唯一
   顶层命令——禁止用 `&`/&&/管道嵌入其他命令（父任务终结将丢失唤醒）」**；
   文案变更同步 orchestration 技能真本「交付判读与决策点」段。
3. `reconcile()`/status：watch.json 的 `fired` 含事件但组长会话未确认过
   （新增 `fired_ack` 标志，`orch status` 展示 fired 明细行后置位）→ status
   补账段逐条列出未确认事件；杜绝「命中了但没人知道」。
4. （顺带承 233248 已修的同秒命名）确认 `.done`/`orch status` 的 run 摘要
   展示 needs_leader 时附上「同 run 内多次失败」计数提示，防重派盲目。

success_criteria（机械核验）：
- registry 读数 max_turns=150；一次真实 devops 派发 >80 轮不再被截断
  （台账 num_turns>80 且交付 result）；
- `pysci-orch approve`/`--from-backlog` 输出的 [NEXT] 挂载段含新增警示行
  （快照断言）；
- 人工构造「watch fired 未确认」态（写 watch.json）→ `orch status` 列出
  该事件明细；确认一次后不再重复列出；
- 全量套件无回归。
