kind: defect
success_criteria: 「stop 请求一次，全部 `_watchdog-loop` 实例在各自一个轮询周期（≤60s）内退出；`stop` 在锁空闲时也仍可向孤儿投递停止信号」——可用进程计数脚本机械复核：stop 前 N → stop 后 ≤150s 变 0（或 1 后立刻 start）。

**复现**（2026-10-14 13:47–13:55 实测，命令+输出）：
1. 进程计数：`Get-CimInstance Win32_Process | ? { $_.CommandLine -like '*_watchdog-loop*' }).Count` → 连续 4 次读数稳定 **6**（非瞬态；锁文件 `watchdog.lock` 只记 pid 25900 一个）。
2. `pysci-orch watchdog stop` → `[√] 已请求协作停止（目标 pid 25900）` → 30/60/90s 后计数 **4**（只停掉了锁持有者与 1 个同批实例）。
3. 再次 `stop` → `[!] 无运行中的 drain worker（锁空闲），无需停止` → 计数仍 **4**，孤儿永远收不到停止信号。

**成因**：`watchdog.cancel` 是**单消费者**信号（`_consume_stop_request` 命中即自删），且 `stop_watchdog` 走 `request_stop` 前被 **lock 门控**——锁持有者退出后，`stop` 直接返回「无需停止」，剩下的孤儿既收不到信号、也再没有可被 stop 的"目标"。孤儿留在原地每 60s 轮询一次；若心跳转 stale，还会**各自**尝试 `_rearm`（只靠 watch-arm.sh 的 token 抢占避免多 listener）。

**修复方向（任一）**：① 改成广播式停止——cancel 记 `ts` 墓碑不自删，实例按自己的 `started` 与 cancel `ts` 比对决定退出；② `stop` 解除 lock 门控（锁空闲时仍投递信号）；③ `start`/`stop` 后做进程清点，多于 1 个实例时逐个点名停止。
