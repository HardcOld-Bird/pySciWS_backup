**场景**：`QUOTA_ERROR_RE`/`CHANNEL_ERROR_RE` 现在是**启动时**从 `state/failure-classes.json` 编译的快照（模块级常量，既有代码与测试都依赖这两个名字）。规格写的是「devops 可扩，改后全链生效」——实际只对**新起的进程**生效：正在跑的 drain worker 与已 import 的 orch 进程仍用旧词表。

**易错点**：改一条 pattern 后若无脑重跑压测/巡检，会看到「改了没生效」，进而怀疑分类器写错了（而真因是词表快照）。这与 README §3.4 已登记的「解析器早于协议」是同一族陷阱（进程启动快照 vs 运行期改动），但那条有明确的兜底与告警，这条没有。

**期望形态**：二选一——① `combined_re()` 每次调用按文件 mtime 失效重编（成本可忽略：单次 `stat` + 至多一次 `compile`），于是「改词表 → 下一跳即生效」；或 ② 明确把语义写成「改词表对**新起进程**生效」，并在 `orch status`/doctor 里显示当前生效词表的来源与 mtime（让「我改了但它还在用旧的」一眼可见，而不是靠猜）。

success_criteria: 改一条 pattern 后，**不重启**既有进程即由 `classify_failure` 反映（方案①，可用一条单测钉：改文件 → 同进程再调 → 新类命中）；或 `orch status` 能读出当前生效词表的 mtime/来源（方案②）。
