kind: defect
success_criteria: `pysci-dev worktree merge` 的 cp 运行态面不再搬运 `orchestration/state/*.lock`（只搬 `sessions-runtime.json` 等状态文件），且全量 pytest 在 worktree 内不再真派生 inspector worker——判据：merge 输出中不出现 `inspector.lock` 行；合并后 main 的 `orchestration/state/inspector.lock`（若存在）其 pid 与 run_log 均指向 main 树；`pytest tests -q` 跑完后 CIM 查不到 run_log 落在 `.qoder/worktrees/…` 下的 `_inspect-worker` 进程。

**证据（本跳实测）**
1. 全量套件真派生 worker：在 worktree 内跑 `pytest "$WT/tests" -q`（2416 passed）期间，PowerShell `Get-CimInstance Win32_Process -Filter "Name='qoderclicn.exe'"` 查到命令行含 `_inspect-worker` 且其 run-log 路径指向 `.qoder/worktrees/20261012-173500-leader…` 的进程，pid 26520（18:46:52 起）、26788/21764（19:00:32 起）——测试把 inspector 队列真点燃，副作用落在主树之外、却写主树运行态。
2. `pysci-dev worktree merge` 把他树锁拖进 main：两次合并各打印一行 `[√] orchestration/state/inspector.lock（new）`，把 worktree 侧 pid 26520 / 14956 的锁 cp 进 main，使 main 认到一个 **pid 与 run_log 都不属于它** 的锁——`orch status` 的判活面据此会误判有 worker 在跑。我已手动删除 main 侧该 lock 文件（`ls` 核对后），否则下一跳会被这把假锁挡住。
3. 同族：`git checkout -- .` 之类整树还原在 worktree 内是自我销毁操作（本跳实伤 6 文件），工具面对此无提示——若 `pysci-dev worktree` 能在 merge/remove 前顺带报告「本 worktree 有 N 个未提交改动」会更安全。

**建议（不擅自改别人职责面，交组长裁决）**
- 测试侧隔离 worker 派生：`ensure_inspector` 在 `PROJECT_ROOT` 非主树（或检测到 cwd 为 worktree）时直接跳过派生，或改由 fixture 注入假 worker；
- `worktree merge` 的 cp 运行态白名单收窄到 `sessions-runtime.json`（排除 `*.lock`），锁的归属判据仍以 pid+run_log 双锚；
- 顺带与 `suggestions/20261012-185838-devops.md` 里那条「接管 rc=1 跳时未对原 pid 判活、导致两套同源实现并发落同一面 + worktree 被 reset」一并处置——同属「接管/回收前不重算 worktree 与种子的归属账」这一处根因。
