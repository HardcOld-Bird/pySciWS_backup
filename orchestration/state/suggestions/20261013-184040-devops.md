**缺陷：`remedy_shape` 有**两个真源**（findings 台账行 vs backlog 条目），而执法只读后者——组长改了前者，任务书仍注入「change 缺判决 → 交付 blocked」的陈旧指令**

现象：组长本单裁定 `remedy_shape=restore` 并**按其附注写入 findings 行**（实测该行现为 `remedy_shape = restore`、`judgment = leader-ruling@2026-10-13：…→ restore`）。但本单任务书正文仍注入了「**修复形状约束（remedy_shape=change…）**…直接交付 <blocked>」整段。

复现（三命令对盘）：
1. `python -c "import json;[print(json.loads(l)['remedy_shape'], json.loads(l)['judgment'][:20]) for l in open('orchestration/state/inspector/findings.jsonl',encoding='utf-8') if 'insp-20261013-045910' in l]"` → 实际 `restore leader-ruling@2026-10`（findings 行已是 restore）；
2. `python -c "import json;d=json.load(open('orchestration/state/backlog.json',encoding='utf-8'));print([{k:i.get(k) for k in ('id','remedy_shape','channel')} for i in (d.get('items') or d) if '045910' in str(i.get('id'))])"` → 实际该条目 `remedy_shape` 仍为 change/缺省（**未随 findings 更新**）；
3. `workflow._remedy_shape_instruction()` 的判据是 `item["remedy_shape"]=="change" and channel=="mechanical"` → 据此注入 blocked 指令。

成因：注入读取的是 **backlog item** 的字段，而组长的裁决落在 **findings 行**——同一事实两处存储，无同步。后果有三个方向，都真实：① 组员若照注入执行，会对**已被裁定 restore 的活**交付 blocked，白烧一跳（本次靠对盘 findings + 组长附注才避免）；② 若 someday 反向（findings 说 change 而 backlog 仍是 restore）则注入**静默放行**一段本该过判决的实施——那是免判决通道被绕过的方向，更危险；③ 组长每次裁定都要记得改两处。

**期望形态**：`remedy_shape` 单一真源。或 ① `promote_finding`/组长裁定入口在写 findings 行的同时**同写 backlog item**（一个事务）；或 ② `_remedy_shape_instruction` 改成读 findings 行（按 id 查），backlog item 不再持有该字段；或 ③ 至少在不一致时**出声**（任务书注入一行「findings 与 backlog 的 remedy_shape 不一致：restore vs change，以后者为准/请组长确认」），而不是默默按旧值注入。

success_criteria: 改一处 `remedy_shape`（findings 行）后，同一 id 重派的任务书不再注入与该值矛盾的形状指令——可用单测钉：构造 backlog=change / findings=restore 的条目 → `backlog_task_text()` 不出现「remedy_shape=change…直接交付 <blocked>」段（或出现明确的「两源不一致」告警行）。
