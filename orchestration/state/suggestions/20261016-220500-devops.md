# 废弃 `plan run`：与 `plan advance` 同能力两实现，违反「同一能力绝不保留两份实现」

kind: usability
source: leader
fingerprint: deprecate-plan-run-20261016

## 现象与分析（用户 2026-10-16 提问引发的反思，已获用户明示「未来以大任务为主，可废弃 plan run，无需考虑向后兼容」）

`plan run` 与 `plan advance` 是**同一能力的两份实现**：都做「结算上一环节＋把当前环节任务书派发给成员＋在交接处给出 [NEXT]」，唯一实质差异是交付方式——`run` 同步阻塞到交接，`advance` 入队即返回（事件驱动唤醒）。且两者已发生旗标漂移（run 独有 `--name/--max-turns`，advance 独有 `--dry`），SKILL/command-surface 花两处篇幅解释二者差异，读者须自行辨析；`[NEXT]` 引导还只推阻塞式 `run`（见单 20261016-215946）。

阻塞语义的存量价值已很小：技能铁律要求长任务 `run_in_background`（阻塞优势即被抵消，且有「嵌入即连坐被杀」风险）；组长工作流的交接决策点由「唤醒事件 + [NEXT]」承接（唤醒链刚修复且有 status 补账兜底）；计划外单件事的同步语义由 `plan adhoc` 承接（内部即走 run）。依据 leader-only §2「**同一能力绝不保留两份实现**」，应删其一。事件驱动（M5）是既定方向，故删 `run` 留 `advance`。

## success_criteria:

- `plan run` 从 `pysci-orch` 命令面移除（二选一定案并留痕：直接不可用；或保留为打印「已废弃，请用 plan advance / plan adhoc」的指路 stub）；`plan advance` 承接其独有旗标 `--name`/`--max-turns`（或论证并记录为何不需要）；
- 阻塞原语**保留在内部**供 `plan adhoc` 及全部内部调用点使用：审计 `src/` 内所有调用面（含 adhoc、夜航/自动化路径），`plan adhoc` 阻塞语义回归测试不变；
- `[NEXT]` 引导与 `command-surface.md`/SKILL 文档只讲 `plan advance`（事件驱动）＋ `plan adhoc`（计划外同步），无 `plan run` 残留——**本条吸收 20261016-215946 判据①（其「并列 run/advance」表述以本单为准作废；该单判据② plan new 源文件命名提示仍有效）**；
- `uv run --no-sync pytest tests` 全绿。
