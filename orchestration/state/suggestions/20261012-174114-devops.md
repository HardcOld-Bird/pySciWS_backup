# 改进建议（devops，待审批）

kind: defect
success_criteria：worker 派生时 stdout 不再指向运行日志文件（改 DEVNULL 或分文件），且有一条阳性测试证明「worker 内任何 print 都无法破坏 run 日志」；benchd/inspectd/drain 三条派生路径同形。

**现象**：headless worker 的 stdout 被重定向进本 run 的 `.log`，而 `_log()` 也写同一文件。任何一次 `print()` 都从偏移 0 **覆写整段运行日志**——让路/闸门/派跳过程当场全灭，且 mock 测不出（`_spawn_detached` 被桩时 stdout 不参与）。2026-10-12 实测引爆于 `cmd_inspect_worker` 的收尾 `print(summary)`，run 日志只剩摘要 JSON（已修：commit `0463ee2`，删 print + 加 stdout 静默回归）。

**证据**
```
$ cat orchestration/state/inspector-runs/<run>.log      # 修复前
{...summary JSON...}                                     # 只有摘要，启动/让路/结束行消失
$ 修复后同一命令
[▶] worker 启动 … [y] 让路：devops-drain 正忙 … [√] worker 结束
```
**为什么模式本身仍脆弱**：修复只消除了本次的 print，没有消除「一个文件两个写者、其中一个用 C 语义从 0 覆写」的结构。benchd 与 drain 的 worker 同形（`_spawn_detached` 重定向 stdout→run log），下一个 `print` 只是还没被写出来。建议派生侧收口：stdout/stderr → DEVNULL（或 `<run>.out` 分文件），日志只由 `_log()` 以追加语义写；再钉一条断言「worker 进程 stdout 不是 run 日志 fd」。这属结构裁决、影响三条派生路径，故提案而非本跳擅自改。
