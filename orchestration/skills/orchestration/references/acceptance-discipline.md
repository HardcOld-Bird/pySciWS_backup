## 1. 用户路径测试（UI / 交互改动的验收门槛）

UI / 交互类改动的验收**必须含用户路径测试**——按**用户会走的路径**驱动：
菜单 → Enter 进模块 → 视图 → 逐一按下 footer 广告的**每一个键**并断言可观察效果；
反向断言：未广告的键**无副作用**。

- **函数直调测试不作数**：直接调 `action_*` / 内部函数会绕过视图闸与 footer 一致化，
  正是「`n` 键断裂穿过验收」的成因（测试走了 `t`→`n` 面板路径，菜单→Enter 路径零覆盖）。
- 范例：`tests/skills/orchestration/test_tui_user_paths.py`（f1 立的用户路径 + 键位矩阵）与
  `test_tui_visual_structure.py`（f2 的视觉结构回归——CSS 类 / 组件结构断言，不做像素比对）。
- 文案一致性同属门槛：footer 广告的键 ⇔ 视图 `check_action` 守卫，须覆盖全 action 表。

## 2. 交接验收 = 任务书条目 × 蓝图条款双向核对

交接处（环节收尾 / `plan run` 推进点）**不只对任务书条目**——须与**蓝图**（计划 YAML +
设计文档）**双向**核对：

- 蓝图**有**而任务书**无** → 拆解遗漏：当场补单，或留痕说明为何不纳入本环节；
- 任务书**有**而蓝图**无** → 记变更（蓝图随之更新，或标注偏离）。

只对任务书一侧核对会漏掉整块蓝图条款——m3 的「拆解遗漏」正是这么发生的。

## 3. 占位文案 / 承诺可溯

- 占位文案必须写明**真实归属**：后续单（写明 backlog id）或 E 几（明确阶段）；
  **禁止**「mN 补 / mN 充实 / mN 建」式兑现不了的环节承诺。
- 文档中承诺的功能必须有对应**任务书 / 计划环节 id** 可溯。
- 机械护栏：`dispatch.lint_taskbook` 的 `placeholder-step-promise` 规则（规则表
  `state/taskbook-lint.json`）在派发口检查——命中的环节 id 必须在**对应计划 YAML 的
  steps** 里存在，否则告警（**不阻断**派发）；引号内的引述样例与 grep 判据字面量不计，
  定位不到对应计划即 fail-open。

## 4. 高频查阅维度集中呈现（信息架构硬判据）

**缺陷定式**：交付物按「事项性质」分节是自然写法，而用户实际是**按维度**查阅（时间线 /
地点 / 金额数值 / 待办 / 口径差异 / 责任人）——**高频维度不集中呈现 = 每次查阅都要全文扫读**。
用户 2026-10-15 驳回 tb-20261015-091655-1 原文：「建议补充硬性时间节点章节……建议将所有这些
硬性时间节点集中总结，方便我关注」。凡总结 / 报告 / 综述类交付皆可能重演，与执行者是谁无关。

- **原则（以使用场景为纲）**：交付物组织以用户后续**使用场景**为纲——凡可预判会被
  **反复查询**的维度，必须有**集中章节或索引视图**（时间线就该有专门的时间线章节，
  数值就该有汇总表），不得只按事项性质分节让维度散落。
  原文确实未提供某维度信息时**如实声明**（「原文未提」），不得以省略该节代替。
- **任务书判据化**：总结 / 报告 / 综述类任务书的 `success_criteria` 显式含一条
  「**高频查阅维度集中呈现**（列明该交付的高频维度清单）」。机械可验：抽查清单上每个
  维度在交付物中是否有集中章节 / 索引视图。
- **反推法（设计流程）**：写交付类任务书时先问「**用户拿到后会反复查什么**」，把答案
  写成集中章节清单，落到该任务书的 `success_criteria` 里；维度清单随材料类型走——
  总结类至少覆盖时间（硬性时点 / 截止期），材料含金额 / 地点 / 责任人 / 口径差异者一并列。
