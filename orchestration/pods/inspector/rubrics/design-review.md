# 设计审查 rubric（inspector 专用，护栏级只读层）

> **出处与修订权**：用户指引 v0.6，落点见 `orchestration/README.md` §6（设计审查三原则，2026-10-12 定稿）。
> 本文件是**护栏级**判据：inspector 只依它出判断，不改它。三维的措辞、次序、取舍
> 都归用户——修订须经组长转呈用户授权（照 README §1 护栏条款的规矩）。
>
> **用法**：巡检菜单项 `design-rubric` 每次选定**一个**模块/技能/工具面，逐维过一遍，
> 每条结论落成一条发现（`pysci-inspect finding add`）。三维都属于**判断类**
> （要走 `submit --jury`）——除了「社区优先」里能给出可重跑替代验证的那一支。

## ① 社区优先

调研社区 / GitHub 上有影响力且维护积极的工具，评估它能否**完全或部分**替代自研的
技能模块、脚本或工具面。能替代的，优先替代。

- **判据**：上游是否活跃（近 12 月有提交）、是否有真实用户基数、许可证是否允许、
  接入成本是否低于自研维护成本。
- **为什么要单列一维**：把维护负担转移给社区，项目整体负担随之减轻——自研代码的
  长期成本是「我们一直得养它」，而这条成本在提案里通常看不见。
- **产出形态**：机械证据类发现（附「上游命令 + 实际输出 + 期望输出」，例如
  `uv pip install X && X --version` 的真读数）可自动晋升；只凭印象的「社区好像有」
  属判断类，须经 J。

## ② 反冗余

当社区依赖与自研实现**提供同类功能**时，积极提议去掉其中一份。

- **判据**：两处实现做同一件事吗？做的是同一件事的两个入口，还是一件事的两个必要
  层次？后者不是冗余（例：`workq` 队列原语 vs `benchd` 测量业务语义——前者是形状，
  后者是判据，拆开正是为了不再各写一份）。
- **本项目的高发形态**：同一语义两处实现（双源漂移）。词表、状态机、判据、格式解析
  这四个位置反复出现过「修了一处忘了另一处」，走查时优先扫它们。
- **产出形态**：指认到具体文件与行、能给出「改一处会漏另一处」的复现路径 → 机械证据类；
  只有「看起来重复」→ 判断类。

## ③ LLM 直觉友好

模块设计是否让 LLM **认知负担轻**：不需要读实现内部就能正确使用。

- **判据**：命令名与参数是否望文知义；错误提示是否给出下一步（`[NEXT]` 行的传统）；
  是否有「得先知道某个隐藏约定才不会用错」的暗坑（这类坑每次踩都要写进 AGENTS.md，
  本身就是本维度的证据）；同一概念在不同面是否有不同名字。
- **为什么要问这个**：本项目的直接用户是 agent。人类觉得优雅的显式配置，对 LLM 可能
  是每次都要重新猜的谜题；别扭的设计会稳定地产出 blocked 交付与文档债。
- **产出形态**：举证 = 某次会话/台账里真实发生的误用或其修复成本；无举证则判断类。

## 三维度之外

发现不落在上面三维里的（设施 bug、预算超限、doctor ✗、意图漂移）照常登记——本
rubric 只管「设计审查」这一类巡检，不是巡检的唯一科目。
